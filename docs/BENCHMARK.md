# 基准集（Benchmark）

用来回答一个此前无法回答的问题：**检测到底准不准？**

## 一、当前基准

| 项 | 值 |
|---|---|
| 用例数 | 6 |
| 覆盖分支 | 8.2 / 8.3 / 8.4 |
| 构造方式 | 6 台容器，每台根路径是一个真实 PHP 页面（带 `X-Powered-By`）|
| 准确率 | **100%**（6/6）|
| 误报率 | **0%** |
| 漏报率 | **0%** |
| 验证时间 | 2026-11-25 |

### 用例清单

| 用例 | 镜像 | 端口 | 真相 |
|---|---|---|---|
| BASE-8426-cli | `php:8.4.26-cli` | 18426 | 8.4.26 · 未补丁 |
| BASE-8427-cli | `php:8.4.27-cli` | 18427 | 8.4.27 · 已补丁 |
| BASE-8234-fpm | `php:8.2.34-fpm` | 18234 | 8.2.34 · 未补丁 |
| BASE-8235-fpm | `php:8.2.35-fpm` | 18235 | 8.2.35 · 已补丁 |
| BASE-8335-fpm | `php:8.3.35-fpm` | 18335 | 8.3.35 · 未补丁 |
| BASE-8336-fpm | `php:8.3.36-fpm` | 18336 | 8.3.36 · 已补丁 |

未补丁 3 台、已补丁 3 台 —— **对称设计**，避免"全判未补丁"也能拿高分。

## 二、复现步骤

```bash
# 1. 在实验场启动 6 台容器（每台根路径返回 X-Powered-By）
for c in "base-8426 php:8.4.26-cli 18426" \
         "base-8427 php:8.4.27-cli 18427" \
         "base-8234 php:8.2.34-fpm 18234" \
         "base-8235 php:8.2.35-fpm 18235" \
         "base-8335 php:8.3.35-fpm 18335" \
         "base-8336 php:8.3.36-fpm 18336"; do
  set -- $c
  docker rm -f $1 2>/dev/null
  docker run -d --name $1 -p $3:8080 $2 \
    sh -c 'mkdir -p /www; cd /www; echo "<?php echo PHP_VERSION; ?>" > index.php; exec php -S 0.0.0.0:8080'
done

# 2. 生成 benchmark.json（见 app/data/benchmark.json 的结构）
# 3. 跑评测
python scripts/run_benchmark.py data/benchmark.json
```

## 三、判定口径

`Verdict.status` 取值 `vulnerable` / `patched` / `unknown`：

| 真相 | 检测结果 | 归类 |
|---|---|---|
| 未补丁 | vulnerable | ✅ 正确 |
| 未补丁 | patched | ❌ **漏报** |
| 已补丁 | patched | ✅ 正确 |
| 已补丁 | vulnerable | ❌ **误报** |
| 任意 | unknown | ⚠️ 待确认（不计入错误）|

**只有误报和漏报算失败。** 待确认不算——数据不足时说"不确定"比猜一个好。

## 四、这个基准**不能**证明什么（必须说清）

1. **样本量太小**：6 个用例只能证明"三个分支的版本号识别正确"，
   不能证明"在真实客户环境里的准确率"；
2. **目标太干净**：容器直连、无 WAF、无反向代理、无自定义错误页。
   真实环境里版本号常被隐藏或改写；
3. **只覆盖官方镜像**：Debian/CentOS 自行回移补丁的构建没进基准，
   这类恰恰是版本号判定最容易出错的地方（标记库才是为它准备的）；
4. **没有对抗样本**：伪造 `X-Powered-By` 的场景没测。

要提升可信度，下一步应加：发行版回移构建（如 `php8.2.34-1+deb12u2`）、
隐藏版本头的站点、以及伪造版本号的对抗样本。
