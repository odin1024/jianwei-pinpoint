# 设备识别逻辑说明（v0.5.2 修复后）

> 这份文档回答三个问题：**扫什么、凭什么下结论、这个结论有多可信**。
> 起因：v0.5.1 把一批捷普安全设备误判成 JumpServer 堡垒机、还冒出了深信服/
> 海康威视的品牌。根因不是"签名少"，而是**证据分级缺失**——用服务级证据
> （Server 头）去推厂商级结论（这是谁家的产品）。

---

## 一、扫描流程：五层收敛

```
L0 端口   对 110 个端口做 TCP connect（并发 96）
            ↓ 只保留"能连上"的
L1 协议   对每个端口做协议识别：HTTP(S) 指纹 / TLS 证书 / SSH·FTP·SMTP banner / favicon 哈希
            ↓
L2 存活   必须拿到**有意义的协议响应**才算在线
            · HTTP 任意状态码（含 401/403/404）
            · SSH/FTP/SMTP 非空 banner
            · TCP 连上但零数据 = NAT/tarpit 噪声，不算存活
            ↓
L3 分类   证据分级打分 → 设备类型 / 厂商 / 产品
            ↓
L4 PHP    有无 PHP → SAPI → 版本 → 对比修复基线
```

---

## 二、证据分级：这是"准不准"的关键

| 级别 | 证据 | 能推出什么 | 不能推出什么 |
|---|---|---|---|
| **T1 产品级** | 页面 `<title>`、页面元数据（`meta application-name` / `og:site_name` / `generator` / `<h1>`）、TLS 证书 O/OU/CN、登录路径、`WWW-Authenticate` realm、favicon | **设备厂商 + 具体产品** | — |
| **T2 服务级** | `Server` 头、协议 banner、`Set-Cookie`、响应正文片段 | 只能说明"跑着什么软件/什么技术栈" | **不能推出厂商**（同一家的 Web 服务标识可能被多家复用，反之亦然） |
| **T3 推断级** | 端口画像、MAC OUI | 兜底猜测，必须显式标注"推断" | 不能当作事实，也不进厂商字段 |

打分规则：

```
score = 签名权重 × 字段系数
        标题 ×1.8      —— 最"人写的"产品标签
        T2 字段 ×0.7   —— 服务级证据永远压不过同权重的产品级证据
        其它 ×1.0

同产品取最高分（不累加），避免 "openssh"+"ssh-2.0-openssh" 叠分盖过 "ubuntu"
互证加分：只有 T1 字段之间才给满分互证，凑上 T2 字段只加半份
置信度 = 0.35 + 优势度×0.35 + 强度×0.30
        只靠 T2 得出的结论 **封顶 0.72**
```

## 二·五、指纹技术栈（v0.5.3）

| 技术 | 做法 | 解决什么问题 |
|---|---|---|
| **并发 TCP connect** | 110 个端口 / 96 线程，非 SYN，免 root | 跨平台、容器内可跑 |
| **路径阶梯 + UA 阶梯** | 7 条路径 × 3 个 UA 逐级尝试 | 设备登录页常不在 `/`；部分设备按 UA 返回不同页面 |
| **单跳重定向跟随** | 首页无信息量且返回 3xx 时，跟一次 `Location` | 大量设备 `/ → /login`，真正的标题在跳转后 |
| **页面元数据提取** | `meta application-name` / `og:site_name` / `apple-mobile-web-app-title` / `generator`、`<h1>` 兜底 | **SPA 设备标题是 JS 渲染的（226/235 就是），但 meta 往往写死在源码里** |
| **TLS 取证** | 证书 subject/issuer/SAN、**是否自签**、是否过期、**ALPN 协商结果（h2 / http/1.1）** | 内网设备几乎全是自签证书；ALPN 能区分现代网关与老设备 |
| **favicon 双指纹** | `sha256`（本地聚类）+ **`mmh3(base64)`（Shodan/Fofa 口径）** | 前者做同款互证，后者可把 hash 直接丢进 Shodan/Fofa 搜同款与厂商 |
| **噪声端口识别** | 跨主机统计（见下） | tarpit 网段不产生假设备 |
| **favicon 聚类** | 跨主机同指纹互证（见下） | 给"只拿到 Web 服务标识"的设备补型号 |

> favicon 的 mmh3 是纯 Python 实现的 MurmurHash3 x86_32（与 `mmh3.hash` 逐位一致，
> 已用公认测试向量 `"hello" → 613153351` 锁在 `tests/test_fingerprint.py` 里），
> 不引入任何第三方依赖。

厂商归属规则（v0.5.2 新增）：

1. 最高分结论自带厂商 → 用它；
2. 否则在**同一设备类型**的 T1 命中里找厂商锚点（例如标题里出现"捷普"）；
3. 都没有就留空 —— **宁可显示"未识别"，也不拿 MAC OUI 冒充设备品牌**。

> MAC OUI 只写进"网卡厂商"，并在详情里注明"仅代表网卡/代工厂，不等于设备品牌"。

## 三、两种跨主机技术（单机扫不出来）

### 1. 噪声端口识别

一个 NAT/tarpit 网段里，**每个 IP 的 25/110/143 都能连上但一个字节都不回**。
只看握手会得到 254 台"邮件网关"。

现在的判据（`apply_noise_ports`）：

- 该端口在 **>30% 的可达主机**上"开着**且没有有效响应**"；
- 且本机对它也没有有效响应。

两个条件都满足才剔除，并写进 evidence。**只统计无响应的端口**——
早期版本连"开着的端口"一起统计，结果把 22/80/443 也当噪声剔了。

### 2. favicon 聚类（同款互证）

同一套管理界面的设备 favicon 哈希相同。批扫结束后：

- 先统计"本批次里 favicon → 已知型号"的映射；
- 某个 favicon 恰好只对应**一个**已知型号时，才把该型号补给同指纹但型号未知的设备；
- 对应多个型号（说明这 favicon 是公司 logo，不是产品特征）就**不补**；
- 补出来的型号置信度封顶 0.6，并在 evidence 里写明"favicon 聚类"。

实测本网段：226 与 235 同指纹，但两台都没有型号锚点 → 正确选择"不猜"。

## 四、v0.5.2 修的案例：jump ≠ JumpServer

| 观察到的证据 | v0.5.1 的错误结论 | v0.5.2 的正确处理 |
|---|---|---|
| `Server: Jump_server` / `Jumper` / `jump` | JumpServer 堡垒机（别家开源产品） | 捷普设备的 Web 服务标识（T2，权重 3.0×0.7） |
| 证书 `O=jump, ST=shan'xi`、`support@jump.net.cn` | JumpServer | 捷普内部 PKI（T1，证书域名/属地） |

## 五、怎么加一条签名

```python
# src/p2s/core/signatures.py
_s(Field.TITLE, "捷普web应用防火墙", T.WAF, "捷普", "捷普 WEB 应用防火墙", 8.0)
#   ↑字段      ↑匹配子串(小写)        ↑类型   ↑厂商   ↑产品名          ↑权重
```

约定：

- 子串必须**足够具体**，不能用 `server`/`company`/`localhost`/`jump` 这类泛词；
- 厂商只在**T1 字段**上给（标题、证书、登录路径），不要在 `Server` 头上给厂商；
- 加完跑 `pytest tests/test_identification.py`，里面有"不允许泛词做签名"的守护测试。

## 六、已知局限（继续提升的方向）

| 局限 | 影响 | 可改进方向 |
|---|---|---|
| 标题由 JS 渲染（如 226/235） | 拿不到型号，只能到厂商级 | 用无头浏览器渲染后取 `document.title`（重，需权衡） |
| favicon 聚类需要"同批次有已知锚点" | 单独扫一台时无效 | 建立跨批次的 favicon 知识库（落库后二次判定） |
| 厂商证书词典只覆盖常见的几家 | 小众厂商只能到类型级 | 持续补充证书 O/OU 词典 |
| MAC OUI 表是静态精简表 | 新 OUI 认不出 | 定期从 IEEE 更新（离线包） |
| 端口画像仍是弱证据 | 无标题设备只能"未识别" | 增加更多产品级探测路径（/login、/api/version） |
