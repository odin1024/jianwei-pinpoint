# 配置加固设计（L1 / L1.5 / L2）

> 版本 0.12.0 起提供。核心前提：**平台永远不直接写业务主机。**

## 一、为什么不做"下发命令直接改"

客户生产环境的配置变更敏感点在于：

| 风险 | 后果 |
|---|---|
| 与 Ansible / Puppet 冲突 | 改完下次 converge 被覆盖，问题"复发"且无人知情 |
| 容器内改文件 | 重启即失效 |
| 多实例 | 一台机 5 个 PHP × 2 个 SAPI，改错一个等于没改 |
| 责任边界 | 改配置导致 502，日志里必须能证明"谁改的、改了什么" |

所以采用**包 + 回执**模型：平台只产出材料，人和 Agent 执行，平台校验结果。

## 二、三层能力

### L1 加固包（默认，零写入）

`GET /api/hardening/pack/{host}` 返回 zip，包含：

| 文件 | 作用 |
|---|---|
| `harden.sh` | 执行脚本：预检 → 备份 → 改 → 校验 → 出回执，校验失败自动回滚 |
| `rollback.sh` | 用 `.p2s.bak.<时间戳>` 一键回滚 |
| `diff.patch` | 精确到行的变更预览，**先看再执行** |
| `manifest.json` | 目标文件、原 sha256、动作列表、白名单、预检项 |
| `README.txt` | 人读的操作步骤与边界说明 |

`harden.sh` 的**预检四件套**（任一不过直接退出，不改文件）：

| 检查 | 退出码 |
|---|---|
| 目标文件存在且可写 | 10 / 11 |
| 非容器环境（`/.dockerenv`） | 12 |
| 文件 sha256 与平台记录一致 | 13 |
| 未被 Ansible/Puppet/Salt 托管 | 14 |
| 校验生效值失败（改完立刻比对 `ini_get`） | 30（并自动回滚） |

### L1.5 漂移检测

加固回执校验通过后，平台记录**基线**（key → value）。
之后每次 Agent 上报都会比对基线，不一致即报"配置漂移"，提示可能被配置管理或升级覆盖。
比"改一次"更有价值——它解决的是"改了又变回去"。

### L2 受控执行（需显式申请）

`POST /api/hardening/request` 签发**一次性令牌**（10 分钟有效，绑定 host + 动作哈希），
`GET /api/hardening/pending/{host}` 由 Agent 主动拉取，`POST /api/hardening/revoke/{host}` 撤销。

动作白名单只有三项，写死在生成脚本里：

```
php.ini.set / file.backup / service.reload
```

**没有"执行任意命令"这个动作。** 令牌不是通用执行凭证。

## 三、回执校验

`POST /api/hardening/receipt` 会做四件事，任一不通过即拒绝：

1. 该主机确实签发过加固包；
2. 回执里的动作**必须在签发清单内**（防止夹带）；
3. 动作取值与签发值一致（防止调包）；
4. `before_sha` 与签发时记录的 sha256 一致（防止"包被用在别的机器/别的文件"）。

通过后：资产标记 `hardening_status=verified`，记录 `hardening_applied`、`hardening_after_sha256`，
并把本次应用值写成漂移基线。

## 四、实测记录（2026-10-30）

在 Ubuntu 24.04 主机上用替身 php + 临时 ini 做了完整验证（**未触碰生产 php.ini**）：

| 用例 | 结果 |
|---|---|
| `sh -n harden.sh / rollback.sh` | 语法通过 |
| sha 不匹配 | 退出码 13 ✅ |
| 配置管理托管（文件首行 `; Ansible managed`） | 退出码 14 ✅ |
| 正常执行 | 4 项全部改为安全值，校验 4/4 OK，生成回执 ✅ |
| 校验失败路径 | 自动回滚并退出 30 ✅ |
| 回滚脚本 | 恢复到加固前内容 ✅ |

真实主机 `web-01`：方案识别出 1 项待加固（`session.upload_progress.enabled` 1→0），
加固包 5.8KB 正常下载。

## 五、边界（必须对客户讲清）

- **关闭 `session.upload_progress` 只是减少攻击面**，CVE-2026-109618 的 OOM 路径在 Zend 引擎核心，
  **唯一完整修复是升级 PHP**；
- 脚本不重启服务（只可选 reload），因为重启时机应由运维决定；
- 若主机由配置管理工具托管，脚本会拒绝执行——正确做法是把变更写进配置仓库。
