## 二、最重要的技术收获

### 1. 五条利用链，其中两条**不需要任何应用条件**

来自 [ikow/php2shell-poc README](https://github.com/ikow/php2shell-poc)：

| 链 | 向量 | 前置 Auth | 条件 |
|---|---|---|---|
| A | session 注入 + LFI | 否 | 应用存在任意 LFI |
| B | var_destroy UAF | 是 | 应用调用 `unserialize()` |
| C | handler 不匹配 `__destruct` | 否 | 两个目录的 `serialize_handler` 不同（FPM） |
| **D** | OOM 破坏 → 陈旧 `EG()` | **否** | **无**，任意 endpoint（mod_php） |
| **E** | FPM session OOM → 陈旧 `BG()` | **否** | 生产端任意 `session_start()`；**消费端任意 endpoint**（FPM） |

**对产品的影响（这是本轮最重要的修正）**：
我们原先的判断口径隐含"站点不用 session 就不用担心"，但 Chain E 的消费端是
**任意 PHP 端点**——`rfc1867` 上传进度处理器在 SAPI 启动阶段执行，早于应用代码。
所以：
- `session.upload_progress.enabled=0` 不是"可选加固"，而是**必做项**；
- 结论里不能再用"该站点不使用 session"作为降级理由。

已据此改写 `agent_api._SETTING_ADVICE` 的措辞（见 0.11.0 CHANGELOG）。

### 2. 运行时补丁指纹：`memory_hard_limit_percent`

来自 [php2shell-guard](https://gitee.com/llrrzz-111/php2shell-guard)：用
`ini_get("memory_hard_limit_percent")` 是否存在判断补丁是否编入二进制。

**本机实测验证**（192.168.1.188，Ubuntu 24.04 / PHP 8.3.6，changelog 显示已回移补丁）：

```
$ php -r 'var_dump(ini_get("memory_hard_limit_percent"));'
string(0) ""          ← 指令存在（未打补丁的构建返回 bool(false)）
$ php -r 'var_dump(ini_get("session.upload_progress.enabled"));'
string(1) "1"
```

结论：该指令在修复版构建中确实存在。已实现为 `hostcheck.probe_patch_flag()`，
并接入判定：**指令存在 → 判为已修复；版本说已修但指令不存在 → 判为"无法确定"并标冲突**。
同时写进 Linux / Windows 两个采集脚本（`patch_flag` 字段）。

> 诚实边界：只在一台已打补丁的主机上做了正向验证，**没有未打补丁的二进制做反向验证**。
> 因此它作为"加权证据"接入，不单独作为唯一判据。

### 3. 规则库：我们已经对齐

把 [detection/php2shell.rules](https://raw.githubusercontent.com/ikow/php2shell-poc/main/detection/php2shell.rules)
（13 条 Suricata）与我们的 13 条逐条对照：

| 他们 | 我们 | 结论 |
|---|---|---|
| 2026100 upload_progress 在 multipart body | P2S-REQ-001 | 一致 |
| 2026101 PHPSESSID 作为表单字段 | P2S-REQ-002 | 一致 |
| 2026102 filename 含 PHP 代码 | P2S-REQ-003 | 一致 |
| 2026103 filename 含序列化对象 | P2S-REQ-004 | 一致 |
| 2026104 超长 filename（会话膨胀） | P2S-REQ-005 | 一致 |
| 2026105 chunked multipart | P2S-REQ-006 | 一致 |
| 2026106 URL 中出现 session 路径 | P2S-REQ-007 | 一致 |
| 2026110 响应含 OOM 错误 | P2S-RES-001 | 一致 |
| 2026111 响应含会话销毁失败 | P2S-RES-002 | 一致 |
| 2026112 Set-Cookie 中 PHPSESSID 超长 | P2S-RES-003 | 一致 |
| 2026115 小包探测（阈值 3/60s） | P2S-REC-001 | 一致 |
| 2026116 X-Powered-By 暴露易受影响版本 | P2S-REC-002 | 一致 |
| （无） | P2S-REC-003 扫描器 UA | **我们多一条** |

**结论：规则覆盖面不落后**，差距在"利用链解释"与"修复能力"。

### 4. 极简检查器的设计取舍（openai/php2shell-checker）

它只做版本检查：读 `X-Powered-By` / `Server`，`HEAD` 失败再 `GET`，
**不跟重定向、不看响应体、不发利用探测**；退出码 0/1/3 表示 OK / 可能受影响 / 未知，
并在 README 里明确写"HTTP 头无法判断是否回移了补丁，`OK` 只描述对外宣称的版本"。

值得借鉴的是它的**克制与退出码契约**——适合做 CI 门禁与批量巡检。

### 5. EOL 分支可以打回移补丁

[Anton-Barinov/php2shell-patches](https://github.com/Anton-Barinov/php2shell-patches)
为 PHP 5.4–8.1 提供社区回移（在 OpenCart / WordPress / HestiaCP / aaPanel 上验证过）。
我们 `versions.py` 已区分 `eol_backport_available`，但报告里没给来源——已在文档里补上。

## 四、本轮已落地的改动

1. `hostcheck.probe_patch_flag()` —— 运行时补丁指纹（含"与 changelog 冲突"的降级逻辑）；
2. Linux / Windows 采集脚本输出 `patch_flag`；
3. `_SETTING_ADVICE` 按 Chain D/E 校正，明确"关闭 upload_progress 只是减少攻击面，
   唯一完整修复是升级"；
4. 新增 `session.use_only_cookies` / `session.use_strict_mode` 两条建议。
