## 三、漏洞技术本质

### 3.1 触发点为什么在“业务代码之前”

理解这次事件的关键，是理解 PHP 的请求生命周期：

```
TCP 连接 → Web 服务器（Apache/Nginx）
   ↓
[SAPI 层]  request startup（请求启动）
   ├── 读取 SAPI 参数、初始化 superglobals
   ├── 解析请求体（multipart/form-data / urlencoded）  ← 【漏洞触发点】
   ├── 处理 session.upload_progress（若启用）           ← 【漏洞触发点】
   └── 应用 INI 配置（可能产生 warning/deprecation）    ← 【漏洞触发点】
   ↓
[脚本执行]  include 入口文件 → 框架启动 → 业务逻辑      ← 应用层防护在这里才开始生效
   ↓
[request shutdown] 请求清理 → 释放请求内存 → worker 复用
```

两个漏洞都落在 **request startup 与 request shutdown** 这两个“应用看不见”的阶段。这意味着：

- WordPress/Drupal/Joomla 的安全插件、`disable_functions`、代码审计、CSP、SQL 注入防护 —— **全部无效**
- WAF 只能拦“已知请求特征”，拦不住“构造变形”
- 唯一有效的手段是**更换运行时本身**

### 3.2 CVE-2026-109618：OOM 导致的内存破坏

**根因（官方表述）**：PHP 使用 `longjmp()` 来处理内存耗尽（OOM）错误，以此跳出当前上下文并中止请求处理。在某些上下文中，请求内存在**尚未完全初始化**时就已可被访问；若此时任何一次内存分配失败，PHP 没有正确处理这种“提前退出”，导致请求内存处于非法状态。**失败的分配不需要与被破坏的内存有任何关系。** 随后的 request shutdown 流程会读取该状态或基于它做分支判断，最终导致远程代码执行。

**CWE 归类**：CWE-416（释放后重用）/ CWE-824（未初始化指针访问）/ CWE-1325（内存分配未受控）/ CWE-755（异常条件处理不当）/ CWE-1419（资源初始化不正确）

**如何制造 OOM（官方列出的三条 multipart 途径）**：

| 途径 | 原理 |
|---|---|
| 无有效 Content-Length 的 multipart | 可绕过初始 `post_max_size` 检查，继续供给解码后的 body 数据 |
| 单个 part 携带无限制数量的 header | 在 PHP 内部表示这些 header 的内存开销远大于其网络传输体积，使“看起来合规”的请求击穿 `memory_limit` |
| 空文件控件 + 嵌套字段名 | 空文件控件不计入 `max_file_uploads`，但仍创建完整的文件元数据数组；嵌套字段名会成倍放大数组开销 |

Datadog 给出的实测触发形态：一个 `application/x-www-form-urlencoded` POST，body 中**单个字段名长度约 3.5 MB**，即可在默认 `memory_limit` 下打出 OOM。这比想象中“温和”得多 —— 不需要巨量流量，一个请求就够。

**为什么 mod_php 最危险**：官方明确指出 —— Apache mod_php **无条件**调用 request shutdown 流程，即使 request startup 已经失败。也就是说：请求启动阶段 OOM → 状态非法 → shutdown 仍然去处理这个非法状态 → 触发。**整个过程早于任何应用代码。** FPM 则在 request startup 失败时直接退出子进程，从而避免了消费非法状态（这也是为什么至今没有完整的 FPM 利用链）。

**缓解的官方口径**：补丁移除了 OOM 场景下的 `longjmp()`，改为「延迟的软 OOM（在下一个 VM safe point 触发）+ 达到更高阈值时的硬 OOM（`_exit()` 立即终止）」。shutdown 不再看到非法状态，同时保留了内存限制能力。

> ⚠️ 官方特别警告：**不要**用 `RLIMIT_AS` / `RLIMIT_DATA` 来做内存限制。因为一旦达到限制，`mmap()` 就会失败，重新触发那条脆弱的 `longjmp()` 路径。这是一个“看似加固、实则扩大攻击面”的典型陷阱，必须写进工具的风险提示库。

### 3.3 CVE-2026-109619：残留全局状态导致的 UAF

**五步模型（官方原文拆解）**：

1. 某个可达的 PHP 操作把**归属于请求的状态**存放到全局可访问位置（producer）
2. 该状态未被重置，或在正常重置后又被重新填充
3. PHP 释放请求内存，但常驻 worker 仍保留着指向它的全局状态
4. 同一个 worker 处理下一个请求
5. 某个 PHP 操作在正常请求初始化重置该状态**之前**，读取/释放/分支判断这份过期状态（consumer）

**已被验证的 producer–consumer 组合**：

| 组合 | 说明 | 影响 |
|---|---|---|
| **INI 诊断（request 初始化前）** | 应用非法或已废弃的 INI 设置时产生的 warning/notice/deprecation，会消费过期的错误状态。**不需要是 fatal，也不需要显示或记录** | 最关键：意味着站点只要有一条“无害”的废弃配置（如 `auto_detect_line_endings=1`），就可能成为 consumer |
| **Session 上传进度反序列化 UAF** | Session 模块在上传进度处理中解码 session 数据，将请求级簿记存入 `BG(unserialize)`；致命的分配失败会销毁请求堆，但反序列化器的全局状态已被发布 | 与内存泄露组合后可实现 WordPress/Drupal/Joomla 未授权 RCE |
| **致命错误回溯 UAF** | PHP 在 `EG(last_fatal_error_backtrace)` 中保留最近一次致命错误的回溯；OOM 销毁请求堆却未 undefine 该值；下一请求若提前输出诊断信息，就会访问悬空指针 | 已对 Drupal 演示未授权 RCE（仅 mod_php） |

**特别危险的三点**：

- **`error_reporting` 关不掉**：官方明确说明，全局状态的访问发生在 PHP 决定是否上报/显示/记录 warning **之前**。改 `error_reporting`、用 `@`、关 `display_errors`、关 `log_errors` —— 全部无效。
- **应用不调用 `session_start()` 也能被打**：内存泄露原语在应用从未使用 session 的情况下依然成立，因此是**应用无关**的。
- **配置本身即攻击面**：INI 里那些“历史遗留的废弃配置”，在这次漏洞中从“无害告警”升级为“可利用入口”。

### 3.4 已公开的三个利用原语

Wiz 公开的三个原语，构成了从“内存破坏”到“完整 RCE”的阶梯：

**原语一：远程进程内存泄露（Heartbleed 式）**

```
1. multipart 请求在 request startup 阶段解析（早于模块正常初始化）
2. 上传进度处理提前初始化 Session 状态，把 session id 发布到 PS(id)
3. OOM 在清理完成前中止请求 → 请求堆被销毁 → PS(id) 悬空
4. 同一 worker 的下一个 multipart 请求，在上传进度清理路径上早于 Session 正常初始化
   重置该指针就已经到达 → PHP 把这份悬空指针当作合法的 zend_string 信任
5. PHP 把「被攻击者重新占用的堆内容」URL 编码后写入 PHPSESSID 响应 Cookie
   → 攻击者从自己的响应头里读回服务器进程内存
```

泄露出来的可能是：**数据库口令、认证 token、API key、证书私钥、其他用户的会话数据**。这也是为什么这次事件被类比为 Heartbleed —— 即使不打到 RCE，光是“读内存”就已经是重大数据泄露。

**原语二：upload-progress 反序列化 UAF → 内存破坏原语**

**原语三：致命错误回溯 UAF → 受控内存破坏**

**组合成完整 RCE 的四阶段链（公开研究的三阶段+收尾）**：

| 阶段 | 动作 | 目的 |
|---|---|---|
| 1. Worker 轮换 | 大字段 POST 触发中断，使子进程异常退出，prefork 派生新 worker 继承相同内存映射 | 保证后续请求落在“布局可控”的进程上 |
| 2. 堆地址泄露 | 借输入变量数量告警提前发出响应头，再在会话初始化路径触发 OOM 留下悬空指针；后续请求重占该区域，URL 编码越界读取，把内存管理指针写进 Cookie | **绕过 ASLR 的第一步** |
| 3. 模块基址泄露 | 由析构函数指针反推 libphp 加载基址 | 完成 ASLR 绕过 |
| 4. 命令执行 | 把析构函数指针改写为系统命令函数，沿对象析构路径触发；全程只用 libphp 内部函数，不引入 libc 依赖 | 无文件 RCE |

**这条链的工程含义**：偏移标定需要从目标容器内 `libphp.so` 的 ELF 符号表读取。公开研究者在首次验证时因标定脚本输出目录权限异常而**静默失败**，退回内置参考值，导致连续三次未命中 —— 表面现象是“利用不稳定”，实际是参数错误。这说明：**RCE 的“成功率”高度依赖目标构建与内存布局，但这只是降低概率，不改变暴露事实。**

### 3.5 补丁到底改了什么

| 改动 | 解决的问题 |
|---|---|
| OOM 不再 `longjmp`，改为 safe point 软 OOM | 消除“半初始化状态被 shutdown 消费”的窗口（109618） |
| 超过第二阈值用 `_exit()` 硬终止 | 避免在非法状态上跑正常清理 |
| shutdown 时清理 error/exception 状态 | 消除致命错误回溯 UAF（109619） |
| 在处理早期就初始化序列化与 session 状态 | 消除 upload-progress / 反序列化 UAF（109619） |

**但补丁并不“治愈病根”**：Datadog 指出，哈希表插入仍然在分配 key 之前更新计数器 —— 也就是说「先改元数据、再分配内存」这个**危险模式仍然存在**，补丁只是把周边错误处理改成“分配失败时不再留下半初始化条目”。PHP 团队判断彻底重构的工程量太大，来不及在本次发布中完成。**结论：同类漏洞大概率还会再出现，这是工具长期存在的价值基础，而不是一次性事件。**

### 4.2 SAPI 可利用性矩阵（官方口径）

| SAPI | 官方结论 | 可利用性 |
|---|---|---|
| **Apache mod_php** | 无条件执行 shutdown，请求启动阶段即可触发 | **已演示**：默认配置下、应用代码执行前、单个未认证请求完成 RCE |
| **FrankenPHP** | 源码分析与 mod_php 同构，无条件调用 shutdown | **很可能**可应用无关攻击（未验证） |
| **PHP-FPM** | 启动失败会杀子进程，避免消费非法状态；但正常启动后 OOM 仍可能落到未处理提前退出的上下文 | **受影响**；109618 无完整链，109619 的 session 生命周期 RCE 已在 mod_php + FPM 上验证 |
| **LSAPI（LiteSpeed）** | 模型类似 FPM | 应用相关利用**很可能**（未验证） |
| **php-cgi** | 官方列入影响范围 | 未公开分析 |
| **CLI** | 单次执行、进程退出、无跨请求复用 | 风险低 |

### 4.3 配置可利用性矩阵（检测工具的核心判定依据）

| 配置项 | 默认值 | 与漏洞的关系 | 改动后效果 |
|---|---|---|---|
| `memory_limit` | 128M（常见） | **有限值是可利用的前提**（可控 OOM） | `-1` 可阻断已确认利用路径，但**不是完整缓解**；且 `mmap` 失败仍会回到 `longjmp` |
| `session.upload_progress.enabled` | **On** | 109619 已验证利用路径的 producer | `0` 可切断已演示的 session 路径（部分缓解） |
| `fatal_error_backtraces`（8.5） | 默认 | 109619 的回溯 UAF 路径 | 设 `0` 可移除生产者 |
| `post_max_size` | 8M | 决定能否在“看似合规”下击穿 memory_limit | 保守值 + 前置独立校验有助降低风险 |
| `max_file_uploads` | 20 | 空文件控件不计入 | — |
| `max_input_nesting_level` | 64 | 嵌套字段名放大数组开销 | 降低可减少放大效应 |
| `enable_post_data_reading` | On | 关闭后不解析 body | 可作缓解（业务代价大） |
| `RLIMIT_AS` / `RLIMIT_DATA` | 未设 | **设了反而更危险** | 禁止使用 |
| 废弃 INI（`auto_detect_line_endings`、`mbstring.*`、`iconv.*`、`assert.*` 等） | 部分环境仍存在 | 109619 的 consumer 入口 | 清理废弃配置可减少触发面 |

### 4.4 资产类型风险排序

```
共享虚拟主机（同机多站，一次扫描命中大批）  ██████████ 最高
Apache + mod_php 单机（默认配置即被打）      █████████░ 极高
PHP-FPM 容器（版本滞后 + 长连接复用）        ███████░░░ 高
独立服务器（暴露公网、维护水平参差）          ██████░░░░ 中高
工控设备 Web 管理面（DTU/串口服务器/HMI）     ██████░░░░ 中高（补丁不可达）
Serverless PHP（生命周期短）                  ██░░░░░░░░ 低
```

**工控/物联网是本次最容易被忽视的重灾区**：设备厂商自研 PHP 管理界面，几乎没有漏洞响应机制；升级涉及停机窗口与现场配合；而 PHP 官方对 8.1 及更早只提供源码级 backport 分支，设备厂商普遍无力跟进。结果是这类资产会长期“带病运行”。

## 五、为什么这次事件与以往不同

### 5.1 AI 把“不可利用”变成了“一小时可利用”

- 缺陷在代码里存在了十几年，人类研究者多次触及但无法构造利用链
- Wiz 使用 Wiz Atlas、Gemini 4 Argon、GPT-5.6 Sol 完成漏洞发现、利用开发、攻击检测与补丁验证
- Calif 借助 GPT-5.6 Sol 识别关键漏洞
- OpenAI 独立发现同根因问题并补充攻击向量
- 最终效果：**过去需要顶级专家数月的内存布局工程，被压缩到数小时**

这件事的行业含义不是“又多了一个高危漏洞”，而是：**“利用复杂度”作为安全边界的时代结束了。** 过去企业做风险评估时会说“这个漏洞利用条件太苛刻，先不修”。这条路以后走不通了 —— 苛刻条件会被 AI 抹平，时间是唯一变量。

### 5.2 协同披露机制在本次事件中实质失效

三重泄漏叠加：

1. CVE 编号提前 3 天在网络流传（附错误信息）
2. 发现方误发 PoC 视频
3. 供应链厂商在正式发布前 6 小时推送含修复的镜像（PHP 基金会公开指控，对方称因已有活跃攻击而“无奈为之”）

结果：**防守方失去了“先打补丁再应对”的那段缓冲期**，攻击者在补丁发布前 4 天（10-17）就已开始尝试。这意味着检测工具的设计不能假设“补丁发布日 = 安全起点”，必须能回溯排查**披露前 4 天以上**的日志。

### 5.3 攻击量爬升速度刷新记录

| 时间 | 攻击尝试量 |
|---|---|
| 披露前 10 小时 | 数千次 |
| 披露后 45 分钟 | 数万次 |
| 10-22 | 数百万次 |

从“数千”到“数百万”，用了不到 48 小时。**这决定了工具的扫描性能要求：不是“一天扫完就行”，而是“小时级出结果”。**

## 六、检测的核心难点（工具设计的直接输入）

| 难点 | 具体表现 | 对工具的要求 |
|---|---|---|
| **版本号不可信** | 发行版回移补丁不改版本号；自定义构建版本号可伪造 | 必须做包 changelog 比对、二进制指纹核验 |
| **EOL 分支无解** | 8.1/8.0/7.x 装了最新版仍是漏洞版 | 需内置 EOL 判定与“迁移建议”而非“升级建议” |
| **CLI 版本 ≠ Web 版本** | `php -v` 显示的是命令行二进制，不一定是 Web 实际运行的 | 必须查 SAPI、phpinfo、进程、模块加载 |
| **无文件攻击** | 不落地 webshell，内存中执行 | 文件查杀无效，需日志+进程行为+内存线索 |
| **日志稀疏** | 成功利用可能既不崩溃也不报错，返回 HTTP 200 | 不能以“日志干净”判定安全，需配置与补丁侧证据 |
| **探测本身有风险** | 触发 OOM 本质上是 DoS 行为 | 探针必须分级、限速、可授权、可回滚 |
| **成功证据模糊** | 内存错误在正常站点也会出现 | 需多维关联，单一信号不定性 |
| **构建差异** | 同一版本不同编译参数，内存布局不同 | 判定要落到“是否含补丁”，不是“能否打通” |

## 七、这件事给安全行业的三个结论

**第一，运行时安全是系统性盲区。**
过去十年，安全投入集中在应用层（OWASP Top 10、代码审计、WAF、RASP）。但这次漏洞在运行时内核，所有应用层防护静默失效。企业的资产台账里通常有“服务器型号、OS 版本、中间件版本、应用版本”，但很少有“**解释器版本 + 构建来源 + 补丁级别 + SAPI 类型**”这一层。这次事件把这一层的缺失暴露得非常彻底。

**第二，漏洞管理的瓶颈已经从“发现”转移到“验证”。**
现在的问题不是“不知道有这个漏洞”，而是：
- 我这两千台机器，哪些是真的没修？
- 我的托管商说修了，怎么证明？
- 我的国产发行版回移了没有？
- 我修完之后，之前有没有被打进去？

这三个问题，**没有一个是靠“版本号比对”能回答的**。这就是检测工具真正的市场空间。

**第三，AI 时代的安全产品必须“可验证”。**
当攻击方用 AI 把利用周期压到小时级，防守方唯一能站住的东西是**证据链**：可复现的检测、可追溯的依据、可审计的结论。也就是说，产品竞争力不在“扫得多快”，而在“结论能不能被人信、能不能被监管认、能不能拿去交差”。
