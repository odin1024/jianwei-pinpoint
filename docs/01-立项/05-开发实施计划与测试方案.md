## 1. 实施策略

### 1.1 三条主线并行

```
主线 A（技术可行性）  靶场搭建 → 检测原语验证 → 判定准确率达标
主线 B（产品可用）    CLI → 控制台 → 报告 → 交付
主线 C（差异化）      补丁核验（changelog → 二进制 marker）
```

**关键排序原则**：**先证明“判得准”，再做“做得好看”。**
理由：如果判定准确率不达标，前端做得再漂亮也没有商业价值。所以靶场与检测引擎必须先行 2 周，其他线可以并行但不能倒置。

### 1.2 时间盒与里程碑

| 里程碑 | 周期 | 交付物 | 验收标准 |
|---|---|---|---|
| **M0 立项与靶场** | 第 1–2 周 | 靶场环境、检测原语验证报告 | 能在靶场上稳定区分“已修/未修/回移/造假”四类样本 |
| **M1 CLI 可用版** | 第 3–6 周 | `p2s scan` 可跑通全流程，输出 JSON/Markdown | 单目标扫描 ≤ 30s，结论含证据链 |
| **M2 平台版** | 第 7–10 周 | Web 控制台 + 批量任务 + 报告导出 | 1000 资产任务可跑完，报告可交付客户 |
| **M3 失陷排查 + 处置闭环** | 第 11–13 周 | D6 模块 + 工单 + 复扫验证 | 对模拟攻击日志包能定位到具体请求行 |
| **M4 企业化** | 第 14–16 周 | RBAC、审计、OpenAPI、离线部署包 | 通过内部安全评审与信创环境部署验证 |
| **V1.0 发布** | 第 17 周 | 完整产品 + 文档 + 培训材料 | 全部验收条款通过 |

> 总周期约 4 个月（按 1 名主力 + 1 名前端 + 0.5 名测试估算）。若只有 1 人全栈，建议压缩到 M0+M1+M2 先交付 CLI + 简版控制台（约 8 周）。

### 2.2 靶场自动化

```yaml
# tests/lab/docker-compose.yml 片段
services:
  t01:
    image: php:8.4.26-apache
    volumes: ["./www:/var/www/html"]
    ports: ["8401:80"]
    environment:
      PHP_INI_MEMORY_LIMIT: "128M"
  t02:
    image: php:8.4.27-apache
    ports: ["8402:80"]
  t03:
    image: php:8.3.35-fpm
    ports: ["8403:9000"]
  nginx-t03:
    image: nginx:alpine
    volumes: ["./nginx/t03.conf:/etc/nginx/conf.d/default.conf"]
    ports: ["8404:80"]
    depends_on: [t03]
```

每个靶场容器挂载统一的探针页：

```php
<?php
// www/index.php —— 仅用于本地靶场，绝不用于客户环境
echo "OK\n";
```

**纪律**：靶场内的任何 PoC/验证代码**不得进入产品代码库主干**。放在 `tests/lab/poc/` 且 `.gitignore` 之外的独立分支，配合 CODEOWNERS 限制。

## 3. 测试方案

### 3.1 测试分层

| 层 | 范围 | 工具 | 目标覆盖 |
|---|---|---|---|
| 单元测试 | 版本解析、区间匹配、证据聚合、评分 | pytest | 行覆盖 ≥ 80%，`ranges.py` ≥ 95% |
| 集成测试 | Detector × Runner 组合 | pytest + testcontainers | 每个 Detector 至少 3 个场景 |
| 靶场回归 | 全链路（T01–T15） | pytest + docker-compose | 判定准确率 ≥ 98% |
| E2E | 控制台流程 | Playwright | 核心 6 条用户路径 |
| 性能测试 | 并发、限速、熔断 | locust | 见 3.4 |
| 安全测试 | 工具自身 | 手工 + bandit + 依赖扫描 | 无高危 |

### 3.2 判定准确性测试集（最关键）

**样本构成（200+）**：

| 类别 | 数量 | 说明 |
|---|---|---|
| 未修复（活跃分支） | 60 | 各 SAPI、各配置组合 |
| 未修复（EOL 分支） | 30 | 5.6/7.0/7.4/8.0/8.1 |
| 已修复（官方版） | 40 | 8.2.35/8.3.36/8.4.27/8.5.12 |
| 已修复（回移补丁） | 30 | RHEL/Ubuntu/麒麟/Alpine |
| 版本造假（自编译） | 15 | 版本号高但无补丁 |
| 信息不足（头隐藏+无凭证） | 20 | 期望 UNKNOWN |
| 特殊 SAPI | 10 | FrankenPHP/LSAPI/CGI/CLI |

**判定指标计算**：

```python
def evaluate(predictions, ground_truth):
    # 关键：把 UNKNOWN 单独统计，不能算作"正确"或"错误"
    tp = sum(1 for p, g in zip(predictions, ground_truth)
             if p.verdict == VULNERABLE and g.verdict == VULNERABLE)
    fp = sum(1 for p, g in zip(predictions, ground_truth)
             if p.verdict in (VULNERABLE, LIKELY_VULNERABLE) and g.verdict == PATCHED)
    fn = sum(1 for p, g in zip(predictions, ground_truth)
             if p.verdict == PATCHED and g.verdict == VULNERABLE)   # 最严重
    unknown = sum(1 for p in predictions if p.verdict == UNKNOWN)

    return {
        "precision": tp / (tp + fp) if tp + fp else 1.0,
        "false_positive_rate": fp / len(predictions),
        "false_negative_rate": fn / len(predictions),   # 门槛 ≤ 0.5%
        "unknown_rate": unknown / len(predictions),      # 门槛 ≤ 15%
    }
```

**上线门槛（硬性）**：

| 指标 | 门槛 | 说明 |
|---|---|---|
| 漏报率 | **≤ 0.5%** | 绝不接受“把有漏洞的判成已修复” |
| 误报率 | ≤ 2% | 回移补丁样本必须全对 |
| UNKNOWN 率 | ≤ 15% | 且必须附“下一步采集建议” |
| 结论可复现 | 100% | 重复扫描同一目标结论一致 |

> V2.0 的 AI 辅助研判值得单独说一句：本次事件的攻方用了 AI，防守方同样可以用 —— 但**用法必须相反**：攻方用 AI 生成利用，守方用 AI 归纳证据、解释结论、生成报告。让 AI 做“把 200 条证据讲成人话”，而不是“猜有没有漏洞”。判定必须由确定性引擎完成，AI 只做表达层。这是防止幻觉进入安全结论的红线。
