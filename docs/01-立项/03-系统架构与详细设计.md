## 1. 设计目标与原则

### 1.1 五个设计目标

| 编号 | 目标 | 可度量指标 |
|---|---|---|
| G1 | **结论可信**：每条判定都能追溯到证据 | 100% 结论带证据引用；冲突场景正确率 ≥95% |
| G2 | **零扰动**：默认配置下扫描不影响业务 | 默认模式下不产生 OOM、不产生 5xx、不写目标磁盘 |
| G3 | **可编排**：能进 SOC / CI / 工单系统 | OpenAPI 全覆盖；单任务可横向扩展 |
| G4 | **可离线**：内网、涉密、信创环境可完整运行 | 无外网依赖；ARM64 + x86_64 双架构 |
| G5 | **可演化**：从 PHP2Shell 泛化到运行时漏洞族 | 新增漏洞族不改核心代码，仅加规则包 |

### 1.2 七条设计原则

1. **证据优先于结论**：引擎内部流转的是 `Evidence` 对象，`Finding` 只是证据的聚合视图。
2. **检测分级、风险分权**：不同检测手段有不同的侵入性和置信度，不能混在一起算。
3. **远程不可信、主机为准**：HTTP 侧数据（版本头、错误页）只能作为线索，主机侧/二进制侧才是判据。
4. **默认最保守**：任何可能影响目标可用性的能力，默认关闭 + 二次确认 + 限速 + 可中止。
5. **规则与引擎分离**：漏洞知识、指纹、IoC 全部外置为 YAML 规则包，支持热更新。
6. **任务幂等**：同一资产重复扫描结果可复现（除时序相关项），便于复扫对比。
7. **数据最小化**：采集到的凭证/日志即时脱敏，原始数据加密存储并按期清理。

## 2. 总体架构

### 2.1 分层视图

```
┌──────────────────────────────────────────────────────────────────────────────┐
│  接入层  Web 控制台 │ CLI(p2s) │ OpenAPI │ CI 插件 │ Webhook │ 导入导出        │
├──────────────────────────────────────────────────────────────────────────────┤
│  应用层  ┌──────────┬──────────┬──────────┬──────────┬──────────┐            │
│          │ 资产管理 │ 任务编排 │ 判定引擎 │ 报告中心 │ 处置中心 │            │
│          └──────────┴──────────┴──────────┴──────────┴──────────┘            │
│          横切：RBAC │ 审计日志 │ 配置中心 │ 通知 │ 调度器 │ 限速器            │
├──────────────────────────────────────────────────────────────────────────────┤
│  检测层（Detector Plugin，统一接口）                                          │
│   D1 被动指纹   D2 主动探测   D3 主机核查   D4 补丁核验                        │
│   D5 受控验证   D6 失陷排查   D7 镜像/固件分析                                 │
├──────────────────────────────────────────────────────────────────────────────┤
│  执行层  Probe Runner(async) │ Host Runner(SSH/WinRM) │ Image Runner(离线)     │
│          Sandbox Runner(隔离靶场) │ Parser/Decoder 池                        │
├──────────────────────────────────────────────────────────────────────────────┤
│  数据层  PostgreSQL/SQLite(WAL) │ 对象存储(证据包) │ Redis(队列/缓存)          │
│          TimescaleDB(时序,可选) │ 规则库(文件+DB)                             │
└──────────────────────────────────────────────────────────────────────────────┘
```

### 2.2 部署形态与组件裁剪

| 形态 | 组件 | 适用 |
|---|---|---|
| **单机 CLI**（V0.1） | CLI + Engine + SQLite + 本地规则包 | 应急工程师笔记本、客户现场 |
| **单机一体化**（V1.0） | 全部组件 + SQLite WAL + 内置队列 | 中小企业、内网单点 |
| **集群**（V1.5） | API × N + Worker × N + PostgreSQL + Redis + MinIO | 万台级、托管商 |
| **采集端分离** | 中心 + 轻量 Collector（容器/主机内） | 跨网段、跨云 |

> 设计要点：**同一套代码，按 profile 裁剪**。`profile=cli` 时不启动 Web、不用 Redis、SQLite 单文件；`profile=cluster` 时启用队列与对象存储。避免维护两套代码。

### 2.3 技术选型

| 层 | 选型 | 理由 |
|---|---|---|
| 语言（核心） | **Python 3.12** | 与公司现有 seccheck/pentra 技术栈一致；生态成熟（httpx/paramiko/lxml） |
| Web 框架 | **FastAPI + Uvicorn** | 异步、OpenAPI 自动生成、与现有项目一致 |
| ORM | SQLAlchemy 2.0（async） | 支持 SQLite/PG 双后端 |
| 任务队列 | **ARQ（Redis）** / 单机用内置 asyncio 队列 | 比 Celery 轻，异步原生 |
| HTTP 探测 | **httpx**（HTTP/1.1 + HTTP/2，可控连接复用） | 需要精确控制 keep-alive（跨请求场景判定） |
| 主机采集 | paramiko（SSH）/ pywinrm（WinRM） | 免 Agent |
| 二进制分析 | `pyelftools` + `pefile` | 解析 ELF/PE 构建信息、符号、BuildID |
| 包数据库 | 自研解析器（rpm sqlite / dpkg status / apk installed） | 需要读 changelog，通用库不够 |
| 前端 | **Vue 3 + Vite + TypeScript + ECharts** | 与 seccheck 一致，团队复用 |
| 报告 | WeasyPrint（PDF）/ python-docx（Word）/ openpyxl（XLSX） | 离线可用，不依赖 Office |
| 容器 | Docker / docker-compose / K8s Helm | |
| 测试 | pytest + pytest-asyncio + testcontainers + Playwright | 靶场自动化 |

**为什么核心用 Python 而不是 Go**：本产品的瓶颈不在单包处理速度，而在**协议细节控制、二进制解析、规则表达力、快速迭代**。扫描并发靠 asyncio 已足够（1 万目标/小时级）。若后续需要十万级，再把 Probe Runner 抽成 Go 侧车（接口已按此预留）。

### 3.2 核心接口定义（Python Protocol）

```python
# p2s/core/contracts.py
from __future__ import annotations
from dataclasses import dataclass, field
from enum import Enum
from typing import Protocol, Any

class Confidence(str, Enum):
    CONFIRMED = "confirmed"      # 有直接、可复现的证据
    HIGH = "high"                # 多源一致
    MEDIUM = "medium"            # 单一强证据
    LOW = "low"                  # 仅有线索
    UNKNOWN = "unknown"          # 无法判定（不是"安全"）

class Verdict(str, Enum):
    VULNERABLE = "vulnerable"    # 确认受影响：版本受影响 且 无补丁证据
    LIKELY_VULNERABLE = "likely_vulnerable"
    PATCHED = "patched"          # 确认已修复：有补丁证据（含回移）
    NOT_APPLICABLE = "not_applicable"  # 不适用（如 CLI-only 且无 Web 暴露）
    UNKNOWN = "unknown"

@dataclass(slots=True)
class Evidence:
    detector: str                # 产生证据的检测器
    kind: str                    # version|sapi|ini|changelog|binary|log|file|process
    key: str                     # 归一化键，如 "php.version"
    value: Any
    confidence: Confidence
    method: str                  # 采集方法（便于复核）
    source_ref: str              # 原始出处：URL / 命令行 / 日志行号 / 文件路径
    raw: str | None = None       # 原始内容（脱敏后）
    collected_at: str = ""
    weight: float = 1.0          # 判定权重，规则可覆盖

@dataclass(slots=True)
class DetectionContext:
    asset_id: str
    target: str                  # URL / host / image ref
    profile: str                 # passive|standard|deep|forensic
    allow_intrusive: bool        # 是否允许 B5
    deadline_s: int
    options: dict[str, Any] = field(default_factory=dict)

@dataclass(slots=True)
class DetectionResult:
    detector: str
    evidences: list[Evidence]
    errors: list[str]
    elapsed_ms: int

class Detector(Protocol):
    name: str
    requires: tuple[str, ...]        # 依赖的前置能力，如 ("host_access",)
    risk_level: str                  # none|low|medium|high
    default_enabled: bool

    async def detect(self, ctx: DetectionContext) -> DetectionResult: ...

class Runner(Protocol):
    async def run(self, spec: "RunSpec") -> "RunOutput": ...
```

**关键约束**：`Detector` 不允许直接产出 `Verdict`。判定统一由 `p2s.verdict` 完成，保证“结论可解释、可复算”。

### 3.3 任务编排设计

#### 3.3.1 任务模型

```
Task（一次扫描作业）
 └── Shard（分片，按资产数/耗时切分，可并行、可重试）
      └── Unit（单资产扫描单元）
           ├── Stage 1 资产识别
           ├── Stage 2 并行检测（D1/D2/D3/D4，按 profile）
           ├── Stage 3 可选增强（D5/D6/D7）
           └── Stage 4 判定与落库
```

#### 3.3.2 状态机

```
PENDING → QUEUED → RUNNING → (PAUSED) → SUCCEEDED
                        ↓                    ↓
                     PARTIAL             FAILED
                        ↓
                   需人工复核 → REVIEWED
```

- **断点续跑**：每个 Unit 完成即落库并写检查点；进程重启后从 `PENDING` 的 Unit 继续。
- **幂等**：Unit 以 `(task_id, asset_id, profile, ruleset_version)` 为唯一键，重复执行覆盖而不追加。
- **重试**：网络类错误指数退避最多 3 次；判定类错误不重试（避免把“不确定”刷成“确定”）。

#### 3.3.3 限速与保护（G2 的实现）

三层令牌桶：

| 层 | 粒度 | 默认值 | 说明 |
|---|---|---|---|
| 全局 | 整个任务 | 100 QPS | 防止出口打满 |
| 目标域 | 单 host | 5 QPS | 防止打挂单站 |
| 连接 | 单 host 并发连接 | 4 | 避免触发 WAF/限流 |

**熔断规则**（自动降级，保护客户业务）：

```yaml
circuit_breaker:
  triggers:
    - name: error_spike
      condition: "5xx_rate > 0.3 and samples >= 10"
      action: pause_target_15m
    - name: latency_spike
      condition: "p95_latency > 3 * baseline and samples >= 10"
      action: reduce_concurrency_50pct
    - name: worker_crash_suspect      # 关键：疑似打崩目标
      condition: "connection_reset_rate > 0.2"
      action: abort_target_and_flag
  on_abort: notify_operator          # 必须人工确认才继续
```

> 这条熔断不是“性能优化”，是**法律风险控制**。在 PHP2Shell 场景下，扫描器把目标 PHP worker 打崩是完全可能的（因为漏洞本身就是 OOM 型），必须有自动刹车。

### 3.4 检测引擎执行流程

```
                    ┌─────────────────┐
                    │  DetectionContext│
                    └────────┬────────┘
                             ↓
                 ┌───────────────────────┐
                 │ 能力探测 Capability    │  ← 有无 HTTP？有无凭证？是否镜像？
                 │ （决定哪些 Detector    │
                 │   可执行）             │
                 └────────┬──────────────┘
                          ↓
        ┌─────────────────┼─────────────────┐
        ↓                 ↓                 ↓
   D1 被动指纹       D2 主动探测        D3 主机核查
   (0 风险)          (低风险)           (需凭证)
        └─────────────────┼─────────────────┘
                          ↓
                   ┌──────────────┐
                   │ D4 补丁核验   │  ← 需要 D3 或镜像数据
                   └──────┬───────┘
                          ↓
              ┌───────────┴───────────┐
              ↓                       ↓
      [allow_intrusive?]          D6 失陷排查
        是 ↓  否 ↓                 (需日志/快照)
      D5 受控验证  skip
              └───────────┬───────────┘
                          ↓
                 ┌────────────────┐
                 │ Verdict Engine │  证据聚合 → 冲突消解 → 评分
                 └────────┬───────┘
                          ↓
              Finding + Evidence Chain + Risk Score
```

**并行策略**：D1/D2/D3 并行（互不依赖）；D4 依赖 D3；D5 依赖 D2 的结果（需要先知道 SAPI）；D6 独立，可最后跑（耗时最长）。

### 3.5 判定与评分引擎（`p2s.verdict`）

#### 3.5.1 证据聚合规则

```python
SOURCE_PRECEDENCE = {
    "changelog": 100,     # 包 changelog 含 CVE → 最可信
    "binary":    95,      # 二进制指纹命中补丁构建
    "source":    95,      # 源码含补丁提交
    "ini":       80,      # 配置项实测值
    "sapi":      80,
    "version_local": 70,  # 本机 php -v / phpinfo
    "version_remote": 30, # HTTP 头（可伪造、可隐藏）
    "behavior":  75,      # 行为探测签名
}
```

**冲突消解伪代码**：

```python
def resolve(evidences: list[Evidence]) -> tuple[Verdict, Confidence, str]:
    # 1) 只要有任意"确认已打补丁"的强证据（changelog/binary/source），即判已修复
    patch_proof = [e for e in evidences if e.kind in ("changelog", "binary", "source")
                   and e.value.get("patched") is True and e.confidence in (CONFIRMED, HIGH)]
    if patch_proof:
        return PATCHED, CONFIDENCE_BY_SOURCE[patch_proof[0].kind], \
               f"补丁证据：{patch_proof[0].source_ref}"

    # 2) 有本机版本且落在受影响区间，且无补丁证据 → 确认受影响
    local_ver = pick(evidences, "php.version", sources=("version_local",))
    if local_ver and in_affected_range(local_ver.value) and not patch_proof:
        # 但若为 EOL 分支，需单独标注
        return VULNERABLE, CONFIRMED, f"本地版本 {local_ver.value} 落在受影响区间且无补丁证据"

    # 3) 仅有远程版本 → 只能给"疑似"，因为头部可隐藏/可伪造
    remote_ver = pick(evidences, "php.version", sources=("version_remote",))
    if remote_ver and in_affected_range(remote_ver.value):
        return LIKELY_VULNERABLE, MEDIUM, "仅远程版本线索，需主机侧确认"

    # 4) 什么都没采到 → UNKNOWN（严禁默认判"安全"）
    return UNKNOWN, UNKNOWN, "证据不足"
```

> **第 4 条是产品底线**：`UNKNOWN` 必须显式呈现，并且计入“待核查”而不是“无风险”。OpenAI 工具在这里返回 `UNKNOWN` 并退出码 3，方向是对的；我们要更进一步 —— 给出“下一步该采什么证据”的具体指引。

#### 3.5.2 风险评分模型

```
RiskScore = 100 × (
      0.40 × VersionRisk        # 版本受影响程度
    + 0.25 × SapiExposure       # SAPI 暴露度
    + 0.20 × ConfigExploitability # 配置可利用性
    + 0.15 × Exposure           # 资产暴露面
) × PatchFactor                 # 补丁因子（0.05~1.0）
```

| 因子 | 取值 | 依据 |
|---|---|---|
| **VersionRisk** | 1.0 = 版本明确受影响且 EOL；0.8 = 受影响且活跃分支；0.3 = 无法判定；0.0 = 已确认修复 | 官方版本矩阵 |
| **SapiExposure** | 1.0 = mod_php / FrankenPHP；0.75 = FPM / LSAPI；0.4 = CGI；0.1 = CLI-only | 官方 SAPI 矩阵 |
| **ConfigExploitability** | 按 4.3 节配置矩阵逐项计分（见 `04` 文档明细表） | 官方缓解说明 |
| **Exposure** | 1.0 = 公网直连；0.7 = 公网经 WAF；0.4 = 内网；0.1 = 仅运维网段 | 资产标签 |
| **PatchFactor** | 已修复=0.05；有强补丁证据=0.05；疑似修复=0.35；无证据=1.0 | 证据链 |

**分级映射**：

| 分数 | 等级 | 处置时限 | 动作 |
|---|---|---|---|
| 85–100 | **P0 紧急** | 2 小时内 | 立即升级/下线，启动应急 |
| 65–84 | P1 高 | 24 小时 | 当日升级，临时缓解 |
| 40–64 | P2 中 | 7 天 | 排期升级 |
| 1–39 | P3 低 | 30 天 | 纳入基线管理 |
| 0 | 已修复 | — | 归档，留证 |

**每条评分必须可展开**：UI 上点击分数，展示每个因子的取值、来源证据、计算公式。这是 G1 的落地方式。

### 3.6 失陷排查模块（`p2s.hunt`）

#### 3.6.1 输入

| 输入 | 格式 | 来源 |
|---|---|---|
| Web 访问日志 | Apache/Nginx combined、JSON | 文件/对象存储/日志平台 API |
| PHP 错误日志 | 文本 | 文件 |
| Apache 错误日志 | 文本 | 文件 |
| 文件系统清单 | `find -printf` 输出 / `osquery` 快照 | 主机采集 |
| 进程快照 | `ps` / `/proc` | 主机采集 |
| 网络连接 | `ss -tnp` / `netstat` | 主机采集 |
| 定时任务/用户 | crontab、`/etc/passwd`、authorized_keys | 主机采集 |

#### 3.6.2 检测规则（关联式，非单点判定）

| 规则 ID | 名称 | 逻辑 | 置信度 |
|---|---|---|---|
| `HUNT-001` | 启动期 OOM 聚集 | `Fatal error: Allowed memory size ... exhausted` 且含 `in Unknown on line 0`，同 host 时间窗内 ≥3 次 | MEDIUM |
| `HUNT-002` | OOM + 大 POST 关联 | HUNT-001 前后 60s 内存在 body_size > 1MB 的 POST | HIGH |
| `HUNT-003` | Worker 崩溃 | Apache `AH00052`（段错误退出）/ FPM `child exited on signal 11` | MEDIUM |
| `HUNT-004` | 上传进度探测 | POST 表单含 `PHP_SESSION_UPLOAD_PROGRESS` 且非业务正常调用 | MEDIUM |
| `HUNT-005` | 异常 PHPSESSID | 响应 `Set-Cookie: PHPSESSID=` 值长度 > 基线 P99 或含 URL 编码的二进制特征（`%00`、超长 `%XX` 序列） | HIGH |
| `HUNT-006` | Multipart 异常 | part 数 > 阈值、header 数 > 阈值、字段名长度 > 64KB、深层嵌套 | MEDIUM |
| `HUNT-007` | 空文件控件滥用 | 单请求中空 `filename=""` 字段数远超业务基线 | MEDIUM |

## 7. 安全设计（工具自身）

### 7.1 威胁模型

| 威胁 | 场景 | 对策 |
|---|---|---|
| 工具被当武器用 | 有人拿 CLI 去打第三方 | 强制授权声明 + 目标白名单 + 水印化请求头 + 使用日志 |
| 凭证泄露 | 数据库被拖 | AES-256-GCM + 密钥外置 + 内存中最小驻留 |
| 证据包泄露 | 证据含客户敏感日志 | 导出前自动脱敏 + 加密 zip + 提取码分离 |
| 自身被攻击 | Web 控制台漏洞 | 与扫描目标网络隔离；控制台仅内网；CSP/HSTS |
| 探针被滥用 | D5 反复触发 OOM | 单资产每日 1 次上限；需 `--i-have-authorization` 显式开关 |

### 7.2 合规与法律边界

**必须内置的三道闸**：

1. **授权声明闸**：创建任务时必须勾选/上传授权证明（工单号/合同号），落库并在报告中体现。
2. **目标归属闸**：目标必须属于已登记资产，或显式标记为“第三方授权资产”并附授权文件。
3. **行为自证闸**：所有对外请求附带可识别 UA（`P2S-Guard/1.0 (+authorized-scan; ticket=xxx)`），并全量记录请求元数据（不含 payload 原文），可导出证明“我只做了这些请求”。

**明确禁止的表达**：报告与 UI 中不得出现“已验证可 RCE”“成功利用”等表述。检测结论只能表述为“满足可利用前置条件”，不得宣称已验证代码执行 —— 因为我们**不做** RCE 验证。

### 7.3 审计日志哈希链

```
record_n.hash = SHA256(record_{n-1}.hash || canonical_json(record_n.payload))
```

每日生成锚点（可选：写入第三方时间戳服务或打印归档），保证事后不可篡改。

```
 │            ├───────────>│  校验授权  │            │            │          │

 │            │            │           │            ├──────────>│          │

 │            │<───────────┤<──────────┤  进度推送   │            │          │

 │ 下载报告/工单                                                             │
```

### 9.2 修复验证流程（闭环关键）

```
Finding(P0) → 生成 remediations
   → 客户执行升级
   → POST /remediations/{id}:verify
   → 编排器创建 verify 任务（同一资产，同 profile）
   → 重采证据：版本 + changelog + 二进制指纹 + worker 启动时间
   → 判定：
        patched 且 worker 重启时间 > 升级时间  → 关闭 finding
        patched 但 worker 未重启              → 保持 P1，提示"配置未生效"
        仍 vulnerable                        → 保持 P0，升级为"修复失败"
```

> “worker 未重启”这个判定点是很多工具漏掉的：**改完 ini 不重启 PHP worker，配置根本不生效**。官方明确指出这一点，我们必须做成硬性检查项。

## 11. 扩展性设计：从 PHP2Shell 到“运行时漏洞族”

### 11.1 抽象层次

```
VulnFamily（漏洞族）
 ├── id: php2shell
 ├── matchers: [version_range, sapi, config_requirement, patch_marker]
 ├── detectors: [D1..D6]
 └── scoring_profile: php-runtime
```

新增一个漏洞族，只需提供：

1. **漏洞知识 YAML**（受影响版本、修复版本、SAPI 矩阵、配置前置条件）
2. **补丁标记 YAML**（如何证明“已修复”：包 changelog 关键词、二进制符号/字节特征、源码提交）
3. **判定模板**（哪些证据组合意味着什么）

**无需改代码**即可支持下一批运行时漏洞（例如：Tomcat/JDK 反序列化基线、Node.js V8 缺陷、OpenSSL 版本链、glibc 缺陷）。

### 11.2 这是产品长期价值的所在

PHP2Shell 会过去，但“**版本号不可信 + 运行时是盲区 + 修复无法自证**”这个结构性问题不会过去。先把框架做对，第二个漏洞族就是纯增量。
