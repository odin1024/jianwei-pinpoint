# P2S-Guard 检测引擎技术方案（核心算法篇）

> 文档版本：V1.0
> 定位：本产品的技术护城河所在。阅读对象为安全研发、漏洞研究员、渗透测试工程师。
> 关联：`03-系统架构与详细设计.md` 第 3 章、`docs/rules/php2shell-vuln-db.yaml`

---

## 0. 一句话说清技术路线

**版本号只能做“线索”，不能做“结论”。**
本引擎用五类证据（远程指纹 / 主机事实 / 补丁标记 / 配置状态 / 行为签名）交叉验证，最终输出的是「**该 PHP 运行时是否包含本次安全修复**」这一可证伪的判断，而不是「版本号是否小于 8.4.27」这一可被轻易骗过的比较。

## 1. 为什么“版本号比对”必然失效

先把问题摆清楚，后面的设计才有依据。

### 1.1 四种必然出错的场景

| 场景 | 版本号表现 | 实际状态 | 版本比对结论 | 后果 |
|---|---|---|---|---|
| **发行版回移补丁** | RHEL/Ubuntu/麒麟 回移补丁，版本号仍是 `8.1.2-1kylin1` | **已修复** | 判为受影响 | **误报**（大量，导致信任崩塌） |
| **自编译无补丁** | 自定义构建打了 `8.4.27` 的版本字符串，但源码没合补丁 | **未修复** | 判为已修复 | **漏报**（最危险） |
| **EOL 分支** | `8.1.35`（该分支最新） | **无官方补丁，仍受影响** | 若只比“是否 ≥ 修复版”，可能判为正常 | **漏报** |
| **多版本共存** | CLI 是 8.4.27，Web 跑的是 8.2.20 | **Web 未修复** | 采信 `php -v` → 判已修复 | **漏报** |

OpenAI 开源工具在 README 中也明确承认了其中两条：「HTTP headers cannot tell whether the version contains a backported fix」「Even OK only describes the advertised version - it doesn't verify the installation」。这说明**方向上的共识已经形成**，我们要做的是把它真正实现出来。

### 1.2 由此得出的三条检测公理

> **公理 1**：远程可观测的一切都可被隐藏或伪造，远程证据只能作线索（权重 ≤ 0.3）。
> **公理 2**：唯一可信的“已修复”证据来自**安装物料本身**（包元数据、二进制、源码）。
> **公理 3**：无法取得安装物料时，结论必须是 `UNKNOWN`，而不是“无风险”。

## 2. 五层检测模型

```
┌─────────────────────────────────────────────────────────────────────┐
│ L5 行为签名验证   D5  受控 OOM 探针 → 观测补丁前后行为差异   [可选]  │
├─────────────────────────────────────────────────────────────────────┤
│ L4 补丁标记核验   D4  包 changelog / 二进制特征 / 源码提交   [核心]  │
├─────────────────────────────────────────────────────────────────────┤
│ L3 主机事实采集   D3  SAPI / 真实二进制 / INI / 进程 / 重启时间      │
├─────────────────────────────────────────────────────────────────────┤
│ L2 主动安全探测   D2  非破坏性侧信道，补全 L1 盲区                   │
├─────────────────────────────────────────────────────────────────────┤
│ L1 被动指纹       D1  HTTP 头 / 错误页 / 静态资源 / Cookie 特征       │
└─────────────────────────────────────────────────────────────────────┘
        证据向左汇聚 → 判定引擎 → Finding（含置信度与证据链）
```

| 层 | 侵入性 | 可得性 | 单层置信度 | 是否可独立定性 |
|---|---|---|---|---|
| L1 被动指纹 | 无 | 极高（只要有 URL） | 低（0.3） | ❌ 只能给线索 |
| L2 主动探测 | 低（正常请求量级） | 高 | 中低（0.4） | ❌ 需与 L3/L4 交叉 |
| L3 主机事实 | 无（只读） | 中（需凭证） | 高（0.7–0.8） | ⚠️ 可给“受影响”，不能给“已修复” |
| L4 补丁核验 | 无（只读） | 中 | **极高（0.95）** | ✅ 可单独定性“已修复” |
| L5 行为签名 | **中高（可能崩 worker）** | 中 | 中高（0.75） | ⚠️ 仅作辅助 |
| L6 失陷排查 | 无（读日志） | 中 | 高（0.8） | ✅ 可定性“疑似失陷”（独立维度） |

## 3. D1 被动指纹：把能白拿的信息全部拿到

### 3.1 采集项

| # | 特征 | 采集方式 | 能推出什么 | 可靠性 |
|---|---|---|---|---|
| 1 | `X-Powered-By: PHP/8.4.24` | 任意请求响应头 | PHP 版本（若 `expose_php=On`） | 中（可伪造/可关闭） |
| 2 | `Server: Apache/2.4.69 (Debian)` | 响应头 | Web 服务器类型 → 推断 SAPI 倾向 | 中 |
| 3 | `Server: Caddy` / 特殊头 | 响应头 | 可能为 FrankenPHP | 中 |
| 4 | `Set-Cookie: PHPSESSID=...` | 响应头 | 确认 PHP 会话在用；Cookie 属性差异可侧证版本代际 | 中 |
| 5 | 错误页指纹 | 触发 404/405/500，看响应体 | 框架（Laravel/ThinkPHP/WordPress）+ 部分版本痕迹 | 中 |
| 6 | `?=PHPE9568F3x-...` 类历史侧信道 | 直接 GET | 部分老配置下会返回 PHP/Zend logo 或版本 | **低（已基本失效，仅作兼容保留）** |
| 7 | `composer.json` / `composer.lock` / `vendor/composer/installed.json` | 路径探测 | 应用依赖版本（非运行时，但可辅助判断迁移难度） | 中 |
| 8 | `.env` / `config.php.bak` / `www.zip` | 路径探测 | 配置泄露（可能含 `DB_*`、`APP_KEY`）→ 需告警 | 高（若命中） |
| 9 | `phpinfo` 类页面 | 路径字典（`/phpinfo.php`、`/info.php`、`/i.php`、`/test.php`、`/php_info.php`、`/p.php`） | **全量配置+版本+SAPI+编译参数**（含金量最高） | 极高（若命中） |
| 10 | 静态资源 ETag / Last-Modified | 响应头 | 文件时间 → 推断部署/升级时间 | 低 |
| 11 | `/server-status`、`/server-info`（Apache） | 路径探测 | 模块列表（可确认 mod_php） | 高（若命中） |
| 12 | HTTP/2、header 顺序、`Transfer-Encoding` 处理差异 | 协议层 | 前端是 Nginx/Apache/CDN，辅助判定真实 SAPI | 中 |

### 3.2 关键设计：`phpinfo` 命中即“降维打击”

一旦发现暴露的 `phpinfo()`，等于拿到了：
- `PHP Version`、`Build Date`、`Compiler`、`Architecture`
- `Server API`（`apache2handler` / `fpm-fcgi` / `cgi-fcgi` / `cli-server`）→ **直接决定风险等级**
- `Loaded Configuration File`、`Scan this dir`
- 全部 `ini` 值（`memory_limit`、`session.upload_progress.enabled`、`post_max_size`、`max_file_uploads`…）
- `Registered PHP Streams`、扩展清单、`Thread Safety`

**处置要求**：D1 命中 phpinfo 时，除记录证据外，必须**立即生成一条独立的“信息泄露”高危项**（这本身就是严重问题），并在报告中单列。

> 注意合规：我们**不写入**任何探针文件。绝不采用“上传一个 phpinfo.php 再删掉”的做法 —— 那是入侵行为，且会在客户磁盘留痕。只做只读路径探测。

### 3.3 反指纹规避对抗

| 客户可能做的隐藏 | 我们的应对 |
|---|---|
| `expose_php=Off` | 转 D2 行为探测 + D3 主机核查 |
| WAF 改写/删除版本头 | 采集多路径（首页/404/静态/API）多方法（GET/HEAD/POST）取并集，比对一致性；不一致本身即是“有中间设备”的信号 |
| 返回假版本 | 用 D4 补丁核验推翻（版本可假，changelog 难假） |
| CDN 缓存了旧头 | 加随机 query 打穿缓存；比对 `Age`/`CF-Cache-Status` |

## 4. D2 主动安全探测：不越界的侧信道

### 4.1 设计红线

> **只发“合法客户端可能发出的请求”，不构造畸形到足以触发内存缺陷的请求。**

这条红线决定了 D2 能做什么、不能做什么：
- ✅ 允许：常规 GET/HEAD/POST、常规 multipart（小 body）、错误触发（404/405）、配置项探测
- ❌ 禁止：超大字段名、超多 header、深层嵌套、空文件控件洪水、超大 body —— **这些是 D5 的领域，且需授权**

### 4.2 可用技术

| 技术 | 方法 | 输出 | 风险 |
|---|---|---|---|
| **SAPI 判定** | 对比 `X-Powered-By` 存在性、`Server` token、404 页结构、`Content-Length` 计算方式、HEAD 与 GET 差异 | `apache2handler` / `fpm-fcgi` / `cgi-fcgi` / `cli-server` | 无 |
| **版本代际侧证** | 请求非法参数触发 `Deprecated:`/`Warning:`（若 `display_errors=On`），错误文案格式随大版本变化（如 PHP 8 的 `Deprecated:` 前缀与堆栈样式） | 版本区间（如“8.x 且 ≥8.2”） | 低（仅产生一条 notice） |
| **INI 行为侧证** | 通过“边界行为”推断配置：如上传超大文件看是否返回 `POST Content-Length ... exceeds` （推断 `post_max_size`）、上传超量文件看 `max_file_uploads` 报错 | 关键配置值区间 | 低（会产生一条 warning 日志） |
| **会话机制探测** | 发起带 `PHP_SESSION_UPLOAD_PROGRESS` 的最小上传，观察是否产生进度会话（不触发缺陷规模） | `session.upload_progress.enabled` 状态 | 低 |
| **框架指纹** | 常见路径 + 响应特征 | WordPress/Drupal/Joomla/Laravel/ThinkPHP 及版本 | 无 |
| **WAF/CDN 识别** | 响应头、拦截页特征、误报触发（发送一条无害 XSS 特征串） | 前置防护能力 | 低 |

> 关于「INI 行为侧证」的重要提醒：这类探测会产生**真实的 PHP 警告日志**。必须在报告里说明“本次扫描在你的 error log 中产生了 N 条 warning”，避免客户事后排查时误判为攻击。这是我们和粗糙扫描器的区别。

### 4.3 探测预算控制

每个目标设定**硬预算**，超限即停：

```yaml
probe_budget:
  max_requests_per_target: 60
  max_body_bytes_total: 2_000_000     # 累计发送 body 上限
  max_multipart_parts: 8
  max_field_name_len: 4096            # 远低于触发 OOM 的 3.5MB
  forbid:
    - "field_name_len > 65536"
    - "multipart_parts > 64"
    - "total_headers_per_part > 64"
    - "body > 4MB"
```

**这份 `forbid` 清单不是性能设置，是安全边界。**任何绕过它的代码路径都必须被 Code Review 拦下，并在 CI 里加静态检查（grep 关键常量）。

## 5. D3 主机事实采集：把“Web 到底在跑什么”钉死

### 5.1 采集流程（Linux）

```
Step 1  识别 Web 服务器与 SAPI
        ├─ 进程：ps -eo pid,ppid,cmd | grep -E 'apache2|httpd|nginx|php-fpm|frankenphp|lshttpd'
        ├─ Apache：apachectl -M 2>/dev/null | grep -i php     → 有 php_module 即 mod_php
        ├─ Nginx：nginx -T 2>/dev/null | grep -E 'fastcgi_pass|root'  → 找到 upstream socket
        │         → 沿 socket 找 fpm pool：ls -l /run/php/*.sock; grep -r 'listen' /etc/php/*/fpm/pool.d/
        └─ 判定：mod_php / fpm / cgi / frankenphp / lsapi / cli-server
```

**核心难点：CLI 的 PHP ≠ Web 的 PHP。** 必须用以下三条交叉锁定“真实运行体”：

| 方法 | 命令 | 说明 |
|---|---|---|
| 进程可执行文件 | `readlink -f /proc/<fpm_pid>/exe` | 拿到真实二进制路径 |
| 进程加载的库 | `cat /proc/<apache_pid>/maps \| grep -o '/[^ ]*libphp[^ ]*'` | mod_php 场景下拿到 `libphp.so` |
| 打开的 socket | `lsof -p <fpm_pid> \| grep LISTEN` | 确认 pool 与站点对应关系 |

```
Step 2  取得该二进制的版本与构建信息
        <binary> -v
        <binary> -i | grep -E 'PHP Version|Server API|Build Date|Configure Command|Thread Safety'
        # 注意：php-fpm 的 -i 输出与 php -i 不同，需分开处理
```

```
Step 3  包管理归属与补丁状态
        # 二进制属于哪个包？
        rpm -qf <binary>   /   dpkg -S <binary>   /   apk info -W <binary>

        # RHEL 系：读 changelog（最高价值）
        rpm -q --changelog php-common | grep -nE 'CVE-2026-10961[89]'

        # Debian 系：读 changelog
        zcat /usr/share/doc/php8.4-common/changelog.Debian.gz | grep -nE 'CVE-2026-10961[89]'
        apt changelog php8.4-common 2>/dev/null | grep -E 'CVE-2026-10961[89]'

        # Alpine
        apk info -a php84 | grep -iE 'cve|security'
```

```
Step 4  配置事实
        <binary> --ini                        # 配置文件路径（含 scan dir）
        <binary> -i | grep -E 'memory_limit|session.upload_progress|post_max_size|max_file_uploads|max_input_nesting_level|enable_post_data_reading|expose_php|fatal_error_backtraces'
        # mod_php 额外：per-dir 配置
        grep -rE 'php_value|php_admin_value|php_flag' /var/www /etc/apache2 2>/dev/null
```

```
Step 5  生效性验证（最容易被忽略的一步）
        systemctl show php8.4-fpm -p ActiveEnterTimestamp   # 服务启动时间
        ps -o lstart= -p <pid>                              # worker 启动时间
        # 若 升级时间 > worker 启动时间 → 补丁未生效（旧 worker 仍在跑）
```

> **Step 5 是产品的“隐藏加分项”**。官方明确说“任何配置变更后都必须重启所有 PHP worker，正在运行的 worker 仍会沿用旧配置”。绝大多数扫描器不查这个，导致客户“以为修了其实没生效”。我们要把它做成 P0 检查项。

### 5.2 Windows / IIS 采集

| 项 | 命令 |
|---|---|
| 版本 | `php-cgi.exe -v`、`Get-Item <path> \| Select VersionInfo` |
| SAPI | IIS 管理器配置 或 `%windir%\system32\inetsrv\appcmd list config /section:fastCgi` |
| 目录 | 注册表 `HKLM\SOFTWARE\PHP`、`appcmd list app` 的 `scriptProcessor` |
| 进程 | `Get-Process php-cgi \| Select StartTime,Path` |

### 5.3 容器 / K8s

| 项 | 方法 |
|---|---|
| 容器识别 | `/.dockerenv` 存在、`/proc/1/cgroup` 含 docker/kubepods |
| 镜像身份 | `HostConfig` 不可得时，用 `dpkg -l` + `/etc/os-release` + 二进制 hash 反查指纹库 |
| K8s | downward API 注入 `POD_NAME/IMAGE`；或 `crictl inspect` |
| 只读 rootfs | 若不可执行命令，退化为 D7 镜像离线分析 |

### 5.4 采集脚本安全要求

- 全部命令**只读**（`-q`、`-s`、`-i`、`ls`、`cat`、`grep`），禁止任何写操作
- 不使用 `sudo` 全域提权；需要时仅对特定只读命令授权（`NOPASSWD` 白名单）
- 单次会话命令数 ≤ 40，超时 30s，输出截断 256KB
- 采集前记录目标时区与时间源（后续时间线关联要用）

## 6. D4 补丁级核验：产品的核心差异化

### 6.1 四种核验方法（按置信度排序）

#### 方法 A：包元数据核验（置信度 0.95）

**原理**：发行版的安全更新必然在 changelog 中写入 CVE 编号（这是行业惯例，也是审计要求）。

```bash
# RHEL / CentOS / openEuler / 麒麟
rpm -q --changelog php-common | grep -B2 -A2 'CVE-2026-10961'

# Debian / Ubuntu / 统信
zcat /usr/share/doc/php*-common/changelog.Debian.gz | grep -A3 'CVE-2026-10961'

# Alpine
apk info -a php* | grep -i cve
```

**判定逻辑**：

```
if changelog 含任一 CVE 编号:
    → patched = True, confidence = CONFIRMED
elif 版本 >= 官方修复版本 and 包来源 == 官方 php.net 构建:
    → patched = True, confidence = HIGH
elif 版本 < 官方修复版本 and changelog 不含 CVE:
    → patched = False, confidence = CONFIRMED
else:
    → patched = None（无法判定）
```

**边界情况处理**：

| 情况 | 处理 |
|---|---|
| changelog 被裁剪（容器镜像常见） | 标记 `changelog_unavailable`，降级到方法 B |
| 发行版未写 CVE 编号（不合规但存在） | 用“包构建时间 > 补丁发布日 且 版本号提升”作为弱证据（confidence MEDIUM） |
| 包被 `dpkg --force` 替换 | 方法 B 兜底 |

#### 方法 B：二进制构建指纹（置信度 0.9）

**原理**：同一个 PHP 版本 + 同一套构建参数 → 产物 hash 稳定；打补丁必然改变产物。因此可建立“已知补丁构建指纹库”。

指纹维度（组合使用）：

| 维度 | 获取方式 | 稳定性 | 说明 |
|---|---|---|---|
| 文件 SHA256 | `sha256sum libphp.so` | 高 | 精确匹配已知构建 |
| ELF Build ID | `readelf -n libphp.so` → `.note.gnu.build-id` | 高 | 发行版构建通常保留 |
| 编译器与参数 | `.comment` 段、`php -i` 的 `Configure Command` | 中 | 可用于聚类 |
| Build Date | `php -i` | 中 | 补丁版构建日期必然 ≥ 2026-10-21 |
| 导出符号集合 | `nm -D libphp.so` / `objdump -T` | 中 | 补丁可能增删符号 |
| 特征字节序列 | 对“修复函数”区间做字节级特征提取 | 高 | 见下 |

**特征字节序列（Signature Bytes）方案（推荐重点投入）**：

```
1. 取官方 php-src 8.4.26 与 8.4.27 的构建产物（同参数编译）
2. 二进制 diff，定位发生变化的函数区间（通过符号表对齐）
3. 对每个变化区间，提取长度 32–64 字节、熵值足够高的字节序列作为 "patched-marker"
4. 同时提取 "vulnerable-marker"（8.4.26 中原有、8.4.27 中被删除的序列）
5. 对目标二进制做 marker 扫描：
     命中 patched-marker 且不命中 vulnerable-marker → patched = True
     命中 vulnerable-marker                       → patched = False
     都不命中                                     → 未知（可能版本不同/被 strip/被混淆）
```

> 这套方法的优点是**不依赖符号表**（strip 后仍可用），且对“版本号造假”免疫。缺点是需为每个大版本/每个构建配置维护 marker 集，维护成本集中在指纹库（这是一次性投入，且可复用）。

**当前已知的补丁语义（用于设计 marker）**：
- 补丁移除了 OOM 路径上的 `longjmp()` 调用点
- 新增“延迟软 OOM（下一个 VM safe point 触发）+ 硬 OOM（第二阈值 `_exit()`）”
- shutdown 阶段新增 error/exception 状态清理
- 请求早期新增序列化与 session 状态初始化

因此 marker 应优先取自：**OOM 处理函数、`zend_bailout` 调用点周边、request shutdown 序列、`BG(unserialize)` 与 `PS(id)` 的初始化代码**。

#### 方法 C：源码/自编译核验（置信度 0.9）

| 场景 | 检查项 |
|---|---|
| 有 `.git` | `git -C <src> log --oneline --grep='CVE-2026-10961'`、`git describe --tags`、`git log -1 --format=%ci` |

## 7. D5 受控行为验证：最有效也最危险的一层

### 7.1 原理：补丁前后行为存在可观测差异

| 观测点 | 未打补丁 | 已打补丁 |
|---|---|---|
| OOM 触发位置 | 常见 `in Unknown on line 0`（request startup 阶段） | 软 OOM 延迟到 safe point，报错位置可能落在具体脚本行 |
| Worker 存活 | mod_php 下 worker 存活并继续服务 | 达硬阈值时 `_exit(137)` → 连接直接断开、无 HTTP 响应 |
| 后续请求 | 可继续正常响应 | 可能被 FPM master 拉起新 worker，表现为 PID 变化 |
| 响应完整性 | 通常返回完整错误页 | 可能表现为连接重置 |

> ⚠️ **这些差异不是 100% 稳定**：受 `memory_limit` 设置、worker 模型、前端代理影响。因此 D5 只能作为**辅助证据**（weight 0.75），不能单独定性。

### 7.2 安全执行协议（必须严格执行）

```
前置条件（全部满足才允许执行）
  □ 客户书面授权（工单号入库）
  □ 目标标记为 allow_intrusive = true
  □ 已确认目标 SAPI（mod_php/FPM）
  □ 已确认目标有健康检查手段（能判断是否打挂）
  □ 已通知客户运维（自动发送通知并等待 ACK，可选）
  □ 该资产 24h 内未执行过 D5（幂等 + 防滥用）

执行协议
  1. 前置健康检查：连续 3 次 GET，全部 200 才继续
  2. 单次探测：发 1 个请求，body ≤ 8MB，字段名长度 = min(memory_limit 估计值 × 1.2, 8MB)
  3. 立即后置健康检查：间隔 2s，连续 5 次 GET
  4. 若健康检查失败 → 立即停止该目标全部检测 + 告警"疑似影响业务"
  5. 总计不超过 1 次探测（禁止重试、禁止并发）
  6. 全程记录请求元数据（不含 body 原文），写入"行为自证"日志

禁止
  ✗ 在同一目标上循环探测
  ✗ 在生产流量高峰执行（默认仅允许 00:00–06:00 窗口，可配置）
  ✗ 对未确认 SAPI 的目标执行
  ✗ 对共享虚拟主机执行（一次可能影响数百站点）
```

### 7.3 探测请求构造原则（不提供完整 payload）

本节只描述**约束**，不提供可用的攻击载荷：

| 参数 | 约束 | 理由 |
|---|---|---|
| Content-Type | `multipart/form-data` | 只有该类型进入漏洞代码路径，也只有它能验证 |
| part 数量 | 1–4 | 最小化 |
| 单 part header 数 | ≤ 8 | 不构造“header 洪水” |
| 字段名长度 | 按 `memory_limit` 估算，取 1.2 倍 | 触发 OOM 的最小必要量 |
| 字段值 | 全为随机 ASCII（`A-Z0-9`） | **绝不含任何结构化数据、指针、序列化内容** |
| 文件字段 | 不使用 | 避免“上传”语义，避免落盘 |
| 目标路径 | 首页或已知无害 GET 端点 | 不针对上传接口（避免业务数据污染） |

**核心区别**：攻击载荷需要“在 OOM 后留下可利用状态”，我们的探针只需要“让 OOM 发生一次”。这两者在构造上差异巨大 —— 我们发送的是**纯随机填充**，不含任何用于内存布局的数据结构。这就是“检测”与“攻击”的技术分界线。

## 8. D6 失陷排查：回答“有没有被打进去”

### 8.1 三类信号的关联模型

```
        ┌──────────────┐   ┌──────────────┐   ┌──────────────┐
        │  请求层信号   │   │  运行时信号   │   │  主机层信号   │
        ├──────────────┤   ├──────────────┤   ├──────────────┤
        │ 异常 multipart│   │ OOM 错误聚集  │   │ 新增 PHP 文件 │

        │ 空文件控件洪水│   │ worker 频繁重建│  │ 异常外连      │
        │ 上传进度标记  │   │ shell 子进程  │   │ 文件时间异常  │
        └──────┬───────┘   └──────┬───────┘   └──────┬───────┘
               └──────────┬───────┴──────────────────┘
                          ↓
                 时间窗关联（默认 10 分钟）
                          ↓
              共现 ≥3 类 → 疑似失陷（HIGH）
              共现 2 类 → 需人工复核（MEDIUM）
              单一信号   → 记录但不告警（LOW）
```

### 8.2 日志解析要点

| 日志 | 解析难点 | 处理 |
|---|---|---|
| Apache combined | 字段中可能含转义引号 | 用状态机而非正则 split |
| JSON 格式（云 WAF/ALB） | 字段名不统一 | 提供字段映射配置 |
| PHP error log | 多行堆栈（`[21-Oct-2026 ...]` 开头） | 按时间戳前缀聚合为事件 |
| 轮转日志（.gz/.1） | 需要跨文件按时间排序 | 自动发现 + 流式 merge |
| 时区不一致 | PHP 用本地时区，代理用 UTC | 强制归一化到 UTC，记录原始时区 |

### 8.3 关键规则实现细节

**HUNT-001 启动期 OOM 聚集**

```python
PATTERN_STARTUP_OOM = re.compile(
    r"PHP Fatal error:\s+Allowed memory size of (?P<limit>\d+) bytes exhausted"
    r".*?in Unknown on line 0"
)

def rule_001(events, window="10m", threshold=3):
    hits = [e for e in events if PATTERN_STARTUP_OOM.search(e.message)]
    for cluster in cluster_by_time(hits, window):
        if len(cluster) >= threshold:
            yield Finding(rule="HUNT-001", confidence=MEDIUM,
                          evidence=[e.line_no for e in cluster],
                          note=f"{len(cluster)} 次启动期 OOM，集中在 {window} 内")
```

**HUNT-005 异常 PHPSESSID（内存泄露的强特征）**

```python
def rule_005(resp):
    cookie = resp.headers.get("set-cookie", "")
    m = re.search(r"PHPSESSID=([^;]+)", cookie)
    if not m: return
    val = m.group(1)
    # 正常 PHPSESSID：26 位 [a-z0-9]
    if len(val) > 200:
        yield Finding("HUNT-005", HIGH, detail=f"PHPSESSID 长度 {len(val)}，疑似内存泄露回显")
    if re.search(r"%[0-9A-F]{2}%[0-9A-F]{2}%[0-9A-F]{2}", val):  # 连续 URL 编码
        yield Finding("HUNT-005", HIGH, detail="PHPSESSID 含连续 URL 编码二进制串")
```

> 这条规则的信噪比极高：正常 PHP 生成的 session id 是固定长度的字母数字串。**一旦出现几 KB 的 URL 编码 Cookie，基本可以确定有人正在打内存泄露。**这是本次事件中最有价值的单一检测指标，必须做成核心规则。

## 11. 误报与漏报控制

### 11.1 误报控制（当前最大风险）

| 误报源 | 占比估计 | 对策 |
|---|---|---|
| 发行版回移补丁 | **最高** | 方法 A/B 强证据优先，覆盖版本结论 |
| CDN/WAF 改写的假版本头 | 中 | 多路径采样 + 一致性校验 |

### 11.2 漏报控制（当前最大危害）

| 漏报源 | 对策 |
|---|---|

|---|---|---|

## 13. 版本区间匹配的特殊实现

### 13.1 PHP 版本字符串的坑

```
8.4.27
8.4.27-1ubuntu1.2
8.4.27RC1
8.4.27-dev
8.4.27-1.el9
8.4.27+deb12u1
8.4.27-1kylin1.3
```

必须实现的归一化：

```python
SEMVER_PHP = re.compile(
    r'^(?P<major>\d+)\.(?P<minor>\d+)\.(?P<patch>\d+)'
    r'(?P<pre>[-+]?(?:RC|beta|alpha|dev)\d*)?'
    r'[-+~]?(?P<distro>.*)$', re.I
)
```

**判定规则**：
- 预发布版本（RC/beta/dev）**不得**判为“已修复”，即使数字达标
- 发行版后缀**忽略**，但不代表已打补丁（必须走方法 A/B）
- 比较时以 `(major, minor, patch)` 元组为准，**非**字符串比较

### 13.2 EOL 分支的特殊逻辑

```python
def evaluate(version: str) -> VersionStatus:
    v = parse(version)
    if v.pre:                                  # RC/beta/dev
        return VersionStatus.UNKNOWN
    if (v.major, v.minor) in EOL_BRANCHES:     # 8.1 / 8.0 / 7.x / 5.x
        return VersionStatus.VULNERABLE_EOL    # 无论 patch 号多大
    fixed = FIXED_VERSIONS.get(f"{v.major}.{v.minor}")
    if fixed is None:
        return VersionStatus.UNKNOWN           # 未收录的新分支
    return VersionStatus.PATCHED if v >= fixed else VersionStatus.VULNERABLE
```

> 这个函数是整个引擎最容易写错、也最容易被客户拿来质疑的地方，必须有完整的单元测试覆盖（≥ 80 个用例）。

## 16. 本章结论

这套方案的技术含量不在“能扫 PHP2Shell”，而在三件事：

1. **把“版本号不可信”这个现实，变成可执行的工程方法**（四类补丁证据 + 置信度分级）
2. **把“检测”和“攻击”的边界，画在代码里而不是嘴上**（探针约束白名单 + CI 静态检查）
3. **把“不确定”诚实地输出出来**（UNKNOWN 是一等公民，而不是被吞掉的异常）

第三点最反直觉，但它是安全产品能不能被长期信任的分水岭。这次的教训是：**在 AI 时代，谁敢说自己“全知”，谁就先失去信任。**
