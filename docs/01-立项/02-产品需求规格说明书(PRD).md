# PHP2Shell 检测工具 产品需求规格说明书（PRD）

> 产品代号：**P2S-Guard**
> 版本：V1.0（立项版）
> 关联文档：`01-PHP2Shell事件完整分析报告.md`、`03-系统架构与详细设计.md`、`04-检测引擎技术方案.md`

---

## 1. 产品定位

### 1.1 一句话定义

**P2S-Guard 是一套面向“运行时漏洞”的专项检测与应急处置平台，解决“版本号不可信”前提下的补丁级验证、配置可利用性判定与失陷回溯排查问题。**

第一版聚焦 PHP2Shell（CVE-2026-109618 / CVE-2026-109619），架构上支持后续扩展到其他“运行时/解释器级”漏洞族（如 Java 反序列化基线、Node/V8、OpenSSL、glibc、Log4j 类供应链运行时缺陷）。

### 1.2 为什么不叫“PHP2Shell 扫描器”

因为单纯“扫描”回答不了客户真正的问题。客户在事件中真正要的是四件事：

| 客户的原话 | 真实需求 | 扫描器能不能回答 |
|---|---|---|
| “我到底有多少台受影响？” | 资产与漏洞的**准确**映射 | 部分（版本号可能不准） |
| “托管商说修了，怎么证明？” | **补丁级**验证 | ❌ 不能 |
| “我这套是国产 OS 回移的，算不算修了？” | 发行版/回移补丁识别 | ❌ 不能 |
| “修之前有没有被打进去？” | 失陷排查与证据留存 | ❌ 不能 |

产品的价值就在这三个“不能”上。

## 2. 目标用户与核心场景

### 2.1 用户画像

| 角色 | 场景 | 核心诉求 | 使用形态 |
|---|---|---|---|
| **甲方安全运营（金融/政企/运营商）** | 漏洞通报后 2 小时内要给出“影响面 + 处置建议” | 快、准、可出报告、可交差 | Web 控制台 + 批量任务 |
| **乙方安服/应急响应工程师** | 到场做应急处置，客户不给装 Agent | 免安装、离线可用、证据可留存 | CLI + 单机模式 |
| **托管商/IDC/云厂商** | 上万台共享主机批量核查 | 高并发、低扰动、可编排 | OpenAPI + 无 Agent 远程核查 |
| **设备厂商（工控/IoT）** | 固件里打包了 PHP，无法远程确认 | 固件/镜像离线解析 | 镜像分析模式 |
| **开发团队（DevSecOps）** | 上线前卡住 PHP 基础镜像 | 流水线集成、失败即阻断 | CLI + CI 插件 |

### 2.2 关键场景（按优先级）

**S1 — 应急响应：48 小时影响面盘点（P0）**
> 输入：一批域名/IP 段 + 一批主机凭证（SSH）
> 输出：分级资产清单（确认受影响 / 疑似 / 已修复 / 无法判定）+ 一页决策报告 + 处置工单
> 约束：1 万台以内 2 小时出初版结果；探测动作不得导致业务中断

**S2 — 补丁验证：证明“真的修了”（P0）**
> 输入：单台主机或单站点
> 输出：补丁证据链（包 changelog / 二进制构建指纹 / 配置状态 / worker 重启时间）
> 关键：能区分“版本号低但有回移补丁”和“版本号高但是伪造/自编译无补丁”

**S3 — 失陷排查：回溯 10-17 以来的日志（P0）**
> 输入：Web 日志、PHP error log、Apache error log、文件系统快照
> 输出：可疑请求时间线、可疑进程/文件/外连、Cookie 异常、OOM 异常聚集
> 关键：给出“疑似被打”的证据组合，而不是单一信号

**S4 — 批量资产治理：把 PHP 运行时纳入台账（P1）**
> 输出：全量 PHP 运行时资产画像（版本/分支/SAPI/EOL 状态/补丁级别/责任人/到期日）
> 价值：这次事件的根因是“没人知道自己在跑什么”，台账是唯一解

**S5 — CI/CD 卡口（P1）**
> 在构建阶段检查基础镜像（`php:8.4-apache` 之类），不达标直接阻断发布

**S6 — 托管商多租户巡检（P2）**
> 同一台机器上几百个 vhost，批量出“站点 → PHP 版本 → 风险”映射

## 3. 竞品与差异化

### 3.1 现有方案盘点

| 方案 | 能力 | 检测原理 | 局限 |
|---|---|---|---|
| **OpenAI `php2shell-checker`**（开源免费） | URL 模式 / Server 模式 | 读 `X-Powered-By`、`Server` 头 或本机 `php -v`，做版本区间比对 | 只看**版本字符串**；头部隐藏即 `UNKNOWN`；无法识别回移补丁；不查配置、不查失陷；无批量、无报告、无 API |
| **Wiz** | 云原生 CSPM/CNAPP | 无 Agent 镜像与运行时清单 | 绑定云环境，本地 IDC / 工控不可用；国内落地难 |
| **Tenable / Qualys / Rapid7** | 通用漏扫插件 | 版本指纹 + 部分主动探测 | 插件是“通用模型”，对 backport 误报高；对 109619 这类配置依赖型判定粗 |
| **360 图龙锋 / 国内厂商体检** | 免费体检引流 | 版本 + 少量 PoC | 以“体检报告”为主，缺少可编排 API 与证据链 |
| **自研 Shell 脚本** | `php -v` + `grep` changelog | 人工 | 无法规模化，结论不可复现，无版本管理 |

### 3.2 我们的差异化（必须守住的三条）

**差异化一：补丁级核验，而不是版本号比对**
- 解析包管理器数据库（rpm/dpkg/apk）→ 读 changelog → 匹配 CVE 编号
- 提取 `libphp.so` / `php-fpm` 二进制 → 计算构建指纹 → 比对已知补丁构建库
- 源码部署 → 检测补丁提交特征（源码树 / patch 文件 / 编译参数）

**差异化二：可利用性判定，而不是“有/无漏洞”二值**
- 同样的漏洞版本，`mod_php` 与 `CLI` 的风险差 10 倍
- 同样的版本，`memory_limit=-1` + `session.upload_progress=0` 与默认配置的风险差一个量级
- 输出的是**风险分 + 可利用前置条件清单**，而不是一个红色感叹号

**差异化三：失陷排查与证据链，而不是“扫完就完”**
- 补丁只能关门，回答不了“谁进来过”
- 提供从 2026-10-17 起的日志回溯、异常聚集分析、IoC 匹配
- 所有结论附带证据（原始日志行、命令输出、文件 hash），可导出、可审计、可作为监管报送附件

### 3.3 不做什么（明确边界）

| 不做 | 原因 |
|---|---|
| 不内置完整 RCE 利用代码 | 产品不是武器；且公开 PoC 大量为恶意伪造（有案例会改受害者壁纸） |
| 不做“打穿验证”式检测 | 触发 RCE 等于入侵客户系统，法律与业务风险不可控 |
| 不做通用漏扫 | 通用漏扫是红海，且解决不了本次事件的核心痛点 |
| 不做默认高危探测 | 默认必须“不可能造成业务影响” |

## 4. 功能需求清单

### 4.1 功能架构总览

```
P2S-Guard
├── A. 资产与发现
│   ├── A1 手工导入（域名/IP/URL/资产表）
│   ├── A2 主机凭证批量导入（SSH/WinRM/跳板）
│   ├── A3 容器镜像与固件导入（tar/oci/bin）
│   └── A4 资产标签与责任人
├── B. 检测引擎（核心，详见 04 文档）
│   ├── B1 被动指纹
│   ├── B2 主动安全探测
│   ├── B3 主机侧核查
│   ├── B4 补丁级核验
│   ├── B5 受控行为验证（可选/需授权）
│   └── B6 失陷排查
├── C. 判定与评分
│   ├── C1 证据聚合与冲突消解
│   ├── C2 风险评分与分级
│   └── C3 结论置信度标注
├── D. 处置闭环
│   ├── D1 缓解措施生成（含风险提示）
│   ├── D2 工单与复扫
│   └── D3 修复验证
├── E. 报告与输出
│   ├── E1 一页决策报告（PDF/Word）
│   ├── E2 明细清单（XLSX/CSV）
│   ├── E3 合规映射（等保 2.0 / ISO 27001）
│   └── E4 机器可读（JSON/SARIF）
└── F. 平台能力
    ├── F1 任务调度与限速
    ├── F2 多租户与 RBAC
    ├── F3 审计日志
    └── F4 OpenAPI
```

### 4.2 需求明细（含验收标准）

#### A. 资产与发现

| ID | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| A1 | 支持 URL/域名/IP/CIDR/资产表（CSV/XLSX）导入，自动去重与归一 | P0 | 1 万条导入 < 30s；重复率统计准确 |
| A2 | 支持 SSH 批量凭证（密码/密钥），支持跳板机与 sudo | P0 | 100 台主机并发采集成功率 ≥ 98% |
| A3 | 支持 Docker/OCI 镜像 tar 解析，提取 `libphp.so`、`php`、包数据库 | P1 | 可离线判定镜像是否含补丁 |
| A4 | 资产标签、业务归属、责任人、暴露面（公网/内网） | P1 | 支持按标签批量下发任务 |

#### B. 检测能力（详见 `04-检测引擎技术方案.md`）

| ID | 能力 | 优先级 | 默认开关 | 风险等级 |
|---|---|---|---|---|
| B1 | 被动指纹（HTTP 头、错误页、`phpinfo` 暴露、Cookie 特征） | P0 | 开 | 无 |
| B2 | 主动安全探测（版本/配置侧信道，不触发 OOM） | P0 | 开 | 低 |
| B3 | 主机侧核查（包、二进制、SAPI、INI、进程、重启时间） | P0 | 开（有凭证时） | 无 |
| B4 | 补丁级核验（changelog / 构建指纹 / 源码特征） | P0 | 开 | 无 |
| B5 | 受控行为验证（触发单次 OOM 观察错误签名） | P1 | **关** | 中（需授权+隔离） |
| B6 | 失陷排查（日志回溯、IoC、异常聚集） | P0 | 开 | 无 |

#### C. 判定与评分

| ID | 需求 | 优先级 | 验收标准 |
|---|---|---|---|
| C1 | 多源证据冲突消解（如：远程报 8.1.2，主机证明确有回移补丁 → 判已修复） | P0 | 冲突场景判定正确率 ≥ 95%（基于靶场集） |
| C2 | 输出 0–100 风险分 + P0/P1/P2/P3 分级 | P0 | 评分公式可解释，每项扣分可溯源到证据 |
| C3 | 每条结论标注置信度（确认/高度可能/疑似/无法判定） | P0 | 不允许输出“无置信度标注的绝对结论” |

#### D. 处置闭环

| ID | 需求 | 优先级 | 说明 |
|---|---|---|---|
| D1 | 生成分场景缓解措施（升级/源码回移/临时缓解/下线） | P0 | **必须**带“缓解不完整”与副作用提示（如 `RLIMIT_AS` 会扩大攻击面） |

| D3 | 复扫与修复验证（对比前后证据） | P0 | 能证明“补丁已生效且 worker 已重启” |

|---|---|---|---|
| E1 | 一页决策报告 | P0 | 给领导看：总数/受影响数/最高风险/建议/时间 |
| E2 | 明细清单 | P0 | 给工程师用：资产、版本、SAPI、证据、建议 |
| E3 | 合规映射 | P1 | 等保 2.0 对应条款（如 8.1.4.1 漏洞管理、8.1.4.2 补丁管理） |

#### F. 平台

| ID | 需求 | 优先级 | 说明 |
|---|---|---|---|
| F1 | 任务调度、并发控制、目标限速（QPS/连接数） | P0 | 防止扫挂业务 |
| F2 | 多租户 + RBAC（管理员/扫描员/审计员/只读） | P0 | 与现有 seccheck 角色模型对齐 |
| F3 | 全量审计日志（谁在什么时候对哪个目标做了什么） | P0 | 不可篡改（哈希链） |

## 6. 关键设计约束（来自事件分析的硬性要求）

1. **禁止把“版本号”作为唯一判定依据** —— 这是 OpenAI 工具的短板，也是我们必须越过的门槛。
2. **禁止默认开启任何触发 OOM 的探测** —— 触发 OOM 等于制造 DoS，必须显式授权、单 worker、可回滚。
3. **禁止建议 `RLIMIT_AS`/`RLIMIT_DATA` 缓解** —— 官方明确警告会重新打开脆弱路径。
4. **必须支持“披露前回溯”** —— 排查起点默认 2026-10-17，而非 10-21。
5. **必须标注“成功利用可能不留日志”** —— 不允许让客户误以为“日志干净=安全”。
6. **必须区分 EOL 分支的“升级建议”与“迁移建议”** —— 8.1 及更早没有补丁，只有迁移。

## 8. 商业化设想（供决策参考）

| 形态 | 定价逻辑 | 目标客户 |
|---|---|---|
| 社区版（CLI 开源） | 免费，建立技术口碑 | 开发者、小站长 |

| SaaS 版（域名检测） | 按次/订阅，类似 SSL 证书检测 | 中小企业、托管商 |

> 现实判断：OpenAI 已经免费开源了“版本号检测”，这块**不能再作为卖点**。我们的收费点只能是：**批量 + 补丁级验证 + 失陷排查 + 报告合规 + 本地化部署**。这四点恰好是开源工具和国外 SaaS 都做不了的。

## 9. 风险与假设

| 风险 | 影响 | 应对 |
|---|---|---|
| 客户认为“OpenAI 免费工具够了” | 销售阻力 | 用“回移补丁误报/漏报”实测对比作为杀手锏 demo |
| 主动探测引发业务中断投诉 | 法律与口碑风险 | 默认关闭高危探针；提供“零扰动模式”；扫描前签授权 |
| 漏洞热度 3 个月后衰减 | 需求下降 | 提前把架构泛化为“运行时漏洞检测框架”，用第二个漏洞族验证 |
| PHP 后续补丁再次引入同类问题 | 规则库需持续跟进 | 建立漏洞知识库 + 指纹库的更新机制（订阅 PHP 安全公告 RSS） |
| 国内发行版回移方式不统一 | 判定困难 | 建立发行版补丁特征库，覆盖主流信创 OS |

## 10. 验收总纲

产品达到 V1.0 时，必须能通过以下**实战验收**：

1. 在靶场（覆盖 8.2.34/8.3.35/8.4.26/8.5.11 未修复 + 对应修复版 + 回移补丁版 + EOL 版）上，**判定准确率 ≥ 98%，误报率 ≤ 2%**。
2. 对“版本号显示 8.1.2 但实际已回移补丁”的样本，**必须判为已修复**（这是 OpenAI 工具会误报的场景）。
3. 对“版本号显示 8.4.27 但是自行编译未打补丁”的样本，**必须判为受影响**（这是所有版本比对工具都会漏报的场景）。
4. 对含模拟攻击流量的日志包，**必须能定位到具体请求行并给出证据链**。
5. 全流程扫描**不产生任何可执行载荷**，行为日志可自证。
